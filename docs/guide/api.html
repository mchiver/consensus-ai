The API

Everything the Consensus-AI page does goes through the API, and so does everything an LLM does. It is plain HTTP with JSON bodies. On a Local server every request is the owner; on a Public server a request is a Clerk session or a token, and a bare one is refused (plan User Management, Step 4; plan Clerk, Step 5). A request says who it is with the header X-Consensus-Service: <name>, and what it posts is then recorded as the owner through that service, shown as the byline <name> by <owner>; a run the server started carries Authorization: Bearer <run token>, a token the server made for it and forgets when it ends; a token minted on an account's page (plan User Management, Step 3) makes the request that account, allowed in each project what its role folder there allows (Owners, Members, Service, Watchers), refused with 403 and the reason otherwise; a Clerk session token in the same header is its user, written to the registry from the token's claims at the first sight (Step 4), and refused with license when the person is the Administrator and their license is below Personal (plan The Server, Steps 2 and 4: no project role needs a license; the answer carries Plan, the plan wanted, and Has); any other token is refused. Errors are { "Error": "..." } with the status: 400 a bad body, 401 an unknown token (sign in for a missing or stale session, license for a plan the person lacks), 403 not allowed, 404 not found, 409 not allowed in this state or a stale revision.

Four calls

What waits on the caller, across every project:

curl -s -H "X-Consensus-Service: <name>" http://127.0.0.1:3500/api/waiting

A reply on a thread:

curl -s -X POST -H "X-Consensus-Service: <name>" -H "Content-Type: application/json" \
  -d '{ "Text": "Agreed; the wording I will apply: ..." }' \
  http://127.0.0.1:3500/api/plans/<plan id>/threads/<thread id>/replies

Applying a resolved thread, with the new text of the whole plan and the revision it was made from:

curl -s -X POST -H "X-Consensus-Service: <name>" -H "Content-Type: application/json" \
  -d '{ "Outcome": "The section now says ...", "Revision": 4, "Text": "# The plan\n\n..." }' \
  http://127.0.0.1:3500/api/plans/<plan id>/threads/<thread id>/apply

A new thread on a passage of the text:

curl -s -X POST -H "X-Consensus-Service: <name>" -H "Content-Type: application/json" \
  -d '{ "Text": "Is this the right default?", "Anchor": { "Text": "the words to anchor to" } }' \
  http://127.0.0.1:3500/api/plans/<plan id>/threads

An anchor's Text is matched against the text as it reads, without markdown marks: no backticks or asterisks.

The operations

Every route is an operation of one interface definition (src/Operations.js), of which the REST API, the MCP server and a local model's tools are three faces: the name an MCP client calls the tool by, the route the API serves it at, what it does, and its arguments. The path's parameters are arguments too (:id is Id, :pid Project, :fid Folder, :tid Thread, :n Revision, :name Name); a GET takes the rest as its query, anything else as its JSON body; an answer is JSON at 200 unless the operation says 201. The list is rendered from the definition when the docs are built, so it is what the server serves.

  • me GET /api/me — Who you are to this server: your account, your roles by project, the speakers the rules run over, the default states and the server's version and name.
  • read_view GET /api/view — The look: the project's in the Desktop, the Server's on a Server (Margins, Highlight, Editor, PreviewHidden, Source, ThreadsHidden, TreeHidden, ShowUpdated, SidebarWidth, ThreadsWidth, PreviewWidth), whether you may change it, where it is kept, and its Shape (the choices, the switches, the widths and the defaults, for a form).
  • write_view PUT /api/view — Changes the look: the fields given over the look as it is, null clearing one; in the Desktop it is saved to the project's project.json, on a Server to its settings, by the Administrator and the Managers alone. Arguments: View (object, required): the fields to change.
  • instructions GET /api/instructions — The instructions for an LLM working with this server: what Consensus is, how to call it, what your user's words mean ("check consensus", "your turn", "build it"), the turn and the build loop; This server first, with the API's address and how to say who you are. Read it first.
  • instructions_token POST /api/instructions/token (answers 201) — Mints a token for you for an LLM session in a project, named "LLM session: ", replacing the one of that name; its value answered this once, for the LLM Instructions' copied text. Arguments: Project (string, required): the project's id.
  • read_settings GET /api/settings — The server's settings file, whole, and its path; the Administrator's and the Managers'.
  • write_settings PUT /api/settings — Writes the server's settings (Name, Port, Scope, States, Owner, Tasks, Llms; the Administrator's and the Managers', the Clerk section the Administrator's alone): the fields given replace the file's, any other field stays. Answers whether a restart is needed (Scope and Port take effect at the next start). Arguments: Settings (object): the settings to write; the fields may also be given at the top level.
  • list_plans GET /api/plans — Every plan and document you may see, across projects, each with its state and the tally of its threads; State keeps the plans in that state. Arguments: State (string): only the plans in this state.
  • create_plan POST /api/plans (answers 201) — A new plan, or a document (Kind document), in a project: at Parent (a folder, or a plan for a Subplan), else at the project's root (a document: in its Context folder). A plan starts in the project's first state unless State says otherwise. Arguments: Title (string, required); Text (string): the markdown; empty when not given; Project (string): the project's id; the first project when not given; Parent (string): a folder's id, or a plan's id for a Subplan; Kind (string): plan (the default) or document; State (string): one of the project's states; an Owner's to give.
  • read_plan GET /api/plans/:id — A plan or document whole: its text at its current revision, its summary with the tally of its threads, its threads with their status, anchor and replies, its project, and whether it is the project's Readme (Context). Arguments: Id (string, required): the plan's or document's id.
  • report GET /api/plans/:id/report — The plan, its Subplans and all their threads as one HTML page made for printing: the passages marked and numbered, every reply with who and when. Arguments: Id (string, required): the plan's id.
  • report_markdown GET /api/plans/:id/report.md — The same report as markdown. Arguments: Id (string, required): the plan's id.

  • write_text PUT /api/plans/:id/text — The plan's or document's whole new text as a new revision, made from Revision (refused with the current revision when the text changed since); the threads stay where they were, an anchor no longer found marking its thread detached. Arguments: Id (string, required); Text (string, required): the whole markdown; Revision (integer, required): the revision the text was made from.
  • delete_plan DELETE /api/plans/:id — A plan or document to the trash, its Subplans with it; never the Readme. Arguments: Id (string, required).
  • list_trash GET /api/trash — The trashed plans and documents of every project.
  • empty_trash DELETE /api/trash — Removes every trashed item of every project for good; the owner's.

  • mount_project PUT /api/projects/:pid/mount — Mounts or unmounts a project on this Server ({ Mounted: true | false }); the Administrator's. An unmounted project is read and written by the Administrator alone; every other account sees the mounted ones only. Arguments: Project (string, required): the project's id; Mounted (boolean, required).

Arguments: Name (string): required unless Path holds a project; Path (string): the project's folder.

Arguments: Project (string, required): the project's id; Name (string); States (array): the state names, or lines of text; Include (array); Exclude (array); Commands (array); Tasks (array): the enabled task ids; null enables them all; GitSync (boolean); AutoCommit (boolean); Llm (string): a connection's id, or null; Version (integer): the project version the change was made from; refused when it moved on.

Arguments: Export (object, required): the export file's content; Mode (string): copy or merge, for a project that is here already; Preview (boolean); Into (object): { Project, Parent? }: the project and folder the items go into.
  • create_folder POST /api/projects/:pid/folders (answers 201) — A new folder in a project, at Parent (a folder) or at the root; never in the Context folder. Arguments: Project (string, required): the project's id; Name (string, required); Parent (string): a folder's id; the root when not given; Version (integer): the project version the change was made from.
  • rename_folder PUT /api/projects/:pid/folders/:fid — A folder's new Name; never the Context folder's. Arguments: Project (string, required): the project's id; Folder (string, required): the folder's id; Name (string, required); Version (integer): the project version the change was made from.

  • copy_item POST /api/items/:id/copy (answers 201) — Copies a folder, plan or document into a project's root or one of its folders, whole (text, threads, revisions, Subplans, everything under a folder) with every id new; never the Readme or the Context folder. Arguments: Id (string, required): the item's id; Project (string, required): the project the copy goes into; Parent (string): a folder's id; the root when not given.

Arguments: Id (string, required): the plan's id; Thread (string, required): the thread's id; Outcome (string, required): what was decided and done, recorded on the thread; Text (string): the whole new text; the outcome alone without it; Revision (integer): the revision Text was made from; required with Text; Anchor (object): { Text, Prefix?, Suffix? }: the passage the thread points at after.

Four routes are not operations: GET /api/clerk (everyone, before identify: { On, Required, PublishableKey, FrontendApi, Pricing }, how people sign in through Clerk, never the secret), POST /api/clerk/webhook (Clerk's events, signed with svix-id, svix-timestamp and svix-signature over the raw body; the registry follows them), GET /api/events (below), and POST /api/mcp (below).

MCP

The same operations as tools over the Model Context Protocol, for Codex, Cursor, Claude Desktop, Claude Code and any other client of it: tools/list describes every operation above with its arguments, tools/call performs one as the caller, checked against their role as a request is, posting with the same byline, and answers its JSON as text (a refusal as an error result with the sentence). Two transports, no library:

  • POST /api/mcp: a JSON-RPC 2.0 message, or a batch, in the body, with the same header a request carries (X-Consensus-Service, or Authorization: Bearer <token>); the reply as JSON, a notification answered 202 with nothing, a body that is not JSON the protocol's parse error. Nothing is server-initiated: GET answers 405.
  • consensus mcp <folder> (node bin/mcp.js <folder> [--service <name>]), or node bin/mcp.js --server <url or saved name> [--service <name> | --token <token>] [--project <id or name>]: the stdio transport, a relay on the client's machine to a running server's POST /api/mcp, one message per line in and out. A folder names a project open in the desktop or in consensus <folder>, whose one-project server, the sidecar, keeps its address in <folder>/.consensus/~sidecar.json; the relay reads it at every message, fills in that project for the tools that take one, and answers each request with one message saying so while the folder is not open. --project fills in the project for the tools that take one when the client leaves it out.

A project is given by its id or its name wherever an operation takes one. Working with an LLM says how a client is configured.

The rules, in plain words

  • A thread is contested until its starter or an Owner of the project resolves it (a Member the threads they started; no vote). Resolving accepts the outcome the last reply states.
  • A resolved thread is resolved, waiting to be applied, until someone with write access to the project applies it: an Owner, a Member or a Service account, in person or through an LLM acting for them (a Watcher is refused 403). Applying makes it applied and records who, when, the revision and the outcome.
  • Any reply to a resolved or applied thread reopens it. Reopening never reverts a change already applied.
  • A contested thread waits on its parties, the starter, the project's Owners, everyone who has replied in it and the LLM speakers, except the one who replied last; a person who has not joined in is not waited on. The speaker is the byline, so a run's reply as Claude-CLI by User is a different speaker from User, and a question the LLM asks you still waits on you. A plan's speakers are the owner, one per LLM connection, the Owners of its project, and everyone seen in its threads. A resolved thread waits on the LLM speakers, the ones that apply it, never on a person. An applied thread waits on nobody.
  • A plan's state is set by an Owner of the project (the server's owner is one of every project's) at any time, 403 for anyone else, and does not depend on its threads.
  • One run per plan at a time, and one per connection: a press while either has a run on is queued behind it, in press order (POST /api/runs above).
  • Editing is allowed at any time and makes a new revision. A manual edit changes no thread's status.
  • Anchors hold to the visible text. After every change each anchor is found again; one that cannot be found is detached, and can be re-anchored.
  • A text change carries the revision it was made from; a stale one is refused with the current revision.

Live events

GET /api/events is a stream of Server-Sent Events: one event per change, naming the plan or project and the kind of change. The page uses it to stay in step; a client of your own can too.
