# The API

Everything the Consensus-AI page does goes through the API, and so does everything an LLM does. It is plain HTTP with JSON bodies. On a Local server every request is the owner; on a Public server a request is a Clerk session or a token, and a bare one is refused (plan User Management, Step 4; plan Clerk, Step 5). A request says who it is with the header `X-Consensus-Service: <name>`, and what it posts is then recorded as the owner through that service, shown as the byline `<name> by <owner>`; a run the server started carries `Authorization: Bearer <run token>`, a token the server made for it and forgets when it ends; a token minted on an account's page (plan User Management, Step 3) makes the request that account, allowed in each project what its role folder there allows (Owners, Members, Service, Watchers), refused with 403 and the reason otherwise; a Clerk session token in the same header is its user, written to the registry from the token's claims at the first sight (Step 4), and refused with `license` when the person is the Administrator and their license is below Personal (plan The Server, Steps 2 and 4: no project role needs a license; the answer carries `Plan`, the plan wanted, and `Has`); any other token is refused. Errors are `{ "Error": "..." }` with the status: 400 a bad body, 401 an unknown token (`sign in` for a missing or stale session, `license` for a plan the person lacks), 403 not allowed, 404 not found, 409 not allowed in this state or a stale revision.

## Four calls

What waits on the caller, across every project:

```
curl -s -H "X-Consensus-Service: <name>" http://127.0.0.1:3500/api/waiting
```

A reply on a thread:

```
curl -s -X POST -H "X-Consensus-Service: <name>" -H "Content-Type: application/json" \
  -d '{ "Text": "Agreed; the wording I will apply: ..." }' \
  http://127.0.0.1:3500/api/plans/<plan id>/threads/<thread id>/replies
```

Applying a resolved thread, with the new text of the whole plan and the revision it was made from:

```
curl -s -X POST -H "X-Consensus-Service: <name>" -H "Content-Type: application/json" \
  -d '{ "Outcome": "The section now says ...", "Revision": 4, "Text": "# The plan\n\n..." }' \
  http://127.0.0.1:3500/api/plans/<plan id>/threads/<thread id>/apply
```

A new thread on a passage of the text:

```
curl -s -X POST -H "X-Consensus-Service: <name>" -H "Content-Type: application/json" \
  -d '{ "Text": "Is this the right default?", "Anchor": { "Text": "the words to anchor to" } }' \
  http://127.0.0.1:3500/api/plans/<plan id>/threads
```

An anchor's `Text` is matched against the text as it reads, without markdown marks: no backticks or asterisks.

## The operations

Every route is an operation of one interface definition (`src/Operations.js`), of which the REST API, the MCP server and a local model's tools are three faces: the name an MCP client calls the tool by, the route the API serves it at, what it does, and its arguments. The path's parameters are arguments too (`:id` is `Id`, `:pid` `Project`, `:fid` `Folder`, `:tid` `Thread`, `:n` `Revision`, `:name` `Name`); a GET takes the rest as its query, anything else as its JSON body; an answer is JSON at 200 unless the operation says 201. The list is rendered from the definition when the docs are built, so it is what the server serves.

## MCP

The same operations as tools over the Model Context Protocol, for Codex, Cursor, Claude Desktop, Claude Code and any other client of it: `tools/list` describes every operation above with its arguments, `tools/call` performs one as the caller, checked against their role as a request is, posting with the same byline, and answers its JSON as text (a refusal as an error result with the sentence). Two transports, no library:

- `POST /api/mcp`: a JSON-RPC 2.0 message, or a batch, in the body, with the same header a request carries (`X-Consensus-Service`, or `Authorization: Bearer <token>`); the reply as JSON, a notification answered 202 with nothing, a body that is not JSON the protocol's parse error. Nothing is server-initiated: `GET` answers 405.
- `consensus mcp <folder>` (`node bin/mcp.js <folder> [--service <name>]`), or `node bin/mcp.js --server <url or saved name> [--service <name> | --token <token>] [--project <id or name>]`: the stdio transport, a relay on the client's machine to a running server's `POST /api/mcp`, one message per line in and out. A folder names a project open in `consensus <folder>`, whose one-project server, the sidecar, keeps its address in `<folder>/.consensus/~sidecar.json`; the relay reads it at every message, fills in that project for the tools that take one, and answers each request with one message saying so while the folder is not open. `--project` fills in the project for the tools that take one when the client leaves it out.

A project is given by its id or its name wherever an operation takes one. [Working with an LLM](llm.html#through-mcp) says how a client is configured.
## The rules, in plain words

- A thread is **contested** until its starter or an Owner of the project resolves it (a Member the threads they started; no vote). Resolving accepts the outcome the last reply states.
- A resolved thread is **resolved**, waiting to be applied, until someone with write access to the project applies it: an Owner, a Member or a Service account, in person or through an LLM acting for them (a Watcher is refused 403). Applying makes it **applied** and records who, when, the revision and the outcome.
- Any reply to a resolved or applied thread **reopens** it. Reopening never reverts a change already applied.
- A contested thread waits on its parties, the starter, the project's Owners, everyone who has replied in it and the LLM speakers, except the one who replied last; a person who has not joined in is not waited on. The speaker is the byline, so a run's reply as `Claude-CLI by User` is a different speaker from `User`, and a question the LLM asks you still waits on you. A plan's speakers are the owner, one per LLM connection, the Owners of its project, and everyone seen in its threads. A resolved thread waits on the LLM speakers, the ones that apply it, never on a person. An applied thread waits on nobody.
- A plan's state is set by an Owner of the project (the server's owner is one of every project's) at any time, 403 for anyone else, and does not depend on its threads.
- One run per plan at a time, and one per connection: a press while either has a run on is queued behind it, in press order (`POST /api/runs` above).
- Editing is allowed at any time and makes a new revision. A manual edit changes no thread's status.
- Anchors hold to the visible text. After every change each anchor is found again; one that cannot be found is detached, and can be re-anchored.
- A text change carries the revision it was made from; a stale one is refused with the current revision.

## Live events

`GET /api/events` is a stream of Server-Sent Events: one event per change, naming the plan or project and the kind of change. The page uses it to stay in step; a client of your own can too.
