## What it is for

Today the LLM takes part in Consensus only when Andre types "check consensus" in the terminal. Consensus already knows the exact moment a thread starts waiting on the LLM; that knowledge just sits there until someone asks.

This proposal inverts the relationship: **Consensus calls the LLM itself**, when Andre presses **Send to LLM**, with a prompt that explains the rules and the tools to act through. The LLM reads, replies and applies, and the call ends. Nothing has to reach a terminal session, so the relay, the channel and the watcher from *Notifying Claude from Outline* are no longer needed.

It changes who starts the conversation, not what the conversation is. Everything the LLM does is still a reply or an applied outcome in Consensus, recorded like any other.

## How it would work

1. **You press Send to LLM in the proposal heading.** Nothing else starts a call. Replying, resolving and new threads only leave work waiting; the button shows how many threads are waiting on the LLM, e.g. **Send to LLM (3)**, and is disabled at 0. The server already works this out for `/api/waiting`.
2. **Consensus calls the LLM at once**, one call for everything waiting on it in this proposal. The prompt holds:
   * the rules in plain words, the same ones as in the readme;
   * the proposal at its current revision;
   * every thread with its replies, the ones waiting on the LLM marked;
   * for each waiting thread, the best passages the search finds for it across all proposals, run by Consensus itself;
   * what is expected: reply in each contested thread with the outcome stated plainly, and apply each resolved thread.
3. **The LLM answers with one JSON object.** For each waiting thread, a reply `{ Thread, Reply }`, an apply `{ Thread, Outcome, Text? }`, or nothing. It has no tools: it gets one look at everything it needs, and answers. If it needs an older revision, it says so in a reply.
4. **Consensus carries the answer out**, as the llm participant and through the same rules as the API, so a stale revision or a reply to a thread that is not waiting is refused exactly as it is now.
5. **The call ends.** The page shows the replies live, as it does today. A line in the server log records the call: which proposal, which threads, how long it took, and whether it succeeded.

While a call runs the button reads **LLM working…** and cannot be pressed again, so no two calls overlap on a proposal.

## Which LLM, and how it is called

Configuration, not code: the llm participant in `consensus.json` gets a `Call` setting.

    { "Name": "llm", "Display": "LLM", "Role": "llm", "Token": "...",
      "Call": { "Kind": "claude-cli", "Command": "claude" } }

* **`claude-cli`: Claude Code in headless mode** (`claude -p`), with every tool turned off. It runs on the claude.ai sign-in already on this workstation: no key, no separate bill.
* **`ollama`: a model served by Ollama**, with `Url` and `Model`, the same shape as the `Embedding` setting: `{ "Kind": "ollama", "Url": "http://127.0.0.1:11434", "Model": "..." }`. Ollama can hold the model to the JSON answer's format.

No provider's API is called directly, so Consensus is not tied to any one provider. Every kind gets the same prompt and returns the same JSON answer; a new kind is one small adapter. A participant without `Call` behaves exactly as today, so the terminal way ("check consensus") keeps working alongside.

## Safety

* **No tools at all.** The called LLM has no shell, no files and no network. It only returns an answer, and Consensus decides what to do with it. "Discussion is never an instruction" is enforced by what it can do, not only by what it is told.
* **The server's rules still apply.** Every reply and apply in the answer is made as the llm participant: it cannot resolve, cannot approve, and a stale revision is refused with 409, as now.
* **Only the button starts a call.** Replies, resolves, saved batches and new threads only leave work waiting. The LLM's own replies and applies never start another call, so it cannot talk to itself in a loop.
* **A ceiling on calls.** A setting caps calls per hour (say 20). Past it, threads simply wait, and the page shows that the LLM is paused.

## Costs and limits

* **The called LLM starts fresh every time.** It knows the proposal, the threads and what the search finds, not what was said in the terminal. Anything that matters has to be written into the proposal, which is how it should be; it also means outcomes must be applied faithfully, because the text is the only memory.
* **Time.** A call takes from seconds to a minute or two. Replies appear when it finishes, not as they are typed.
* **Usage.** A `claude-cli` call uses the claude.ai plan's allowance; an `ollama` call costs only the workstation's time. The button and the ceiling keep that bounded.
* **One more moving part in the server:** a queue of calls and a child process.

## Measure first

Before anything is built, each check reported before the next:

1. Does `claude -p` with every tool off reliably return a well-formed JSON answer? Try it by hand on one thread.
2. How long does a typical call take, and how much of the plan's allowance does it use?
3. Can the local model meant for `ollama` write a faithful new whole text for an apply? Try one apply with it.
4. What does the LLM do with a thread it should *not* act on (already answered, waiting on Andre)? The prompt must make "nothing to do" an easy answer.
