# Clerk

Clerk (clerk.com) is the sign-in of Consensus: User Management (rewritten 2026-10-18) keeps no passwords and no sign-in of its own, Clerk identifies people once, and Consensus manages the roles and permissions. This subplan says which parts of Consensus Clerk takes over, which it never touches, how the Clerk application is configured, and how it meets the code. It was drafted on 2026-10-18 while the Clerk application was being created; the decisions were settled the same day (the decisions thread, resolved with no reply): Clerk for network servers only, email code with GitHub and Google, Consensus tokens for machines, Clerk Billing off, the liquicode.com subdomain below, waitlist at launch, and the order of the steps. Steps 2 to 4 were built as User Management Step 4 on 2026-10-19. On 2026-10-20 the model was turned around (the license thread, resolved with two changes): licenses belong to people, not to servers, our one Clerk instance signs in every Consensus server, and the trusted network is gone; the sections below read as the model stands now.


## The license

- **Free is the Local server.** Scope Local or None, no sign-in, the owner's name typed in the Settings popup, unlimited installations. The Users fold holds the owner, with the tokens minted on its page, and the Service accounts the owner makes, each with its tokens, so agents and services on the machine run with a byline of their own; no user accounts and no sign-in. The project role folders stay as they are, since the owner is everything there, and a Service account's token is confined to its folder even on Local.
- **Paid is a single-user license on a Consensus-AI account.** A licensed person may run a Public server (the Docker image is a Public server) and sign in to any Public server where they hold an account; their email and names come from Clerk, and the server's accounts and project roles are what they are since User Management Step 3. The license has a kind, its **Plan**: **Host** runs a Public server, is its Administrator, and does everything below; **User** is an Owner or a Member in projects. A **Watcher** needs an account but no license: they read, and press the tasks that write nothing, which is the Owners' choice when they place them. Service accounts have no license, being tokens.
- **A site license is a Clerk organization.** It carries the License for its members, with Clerk's membership cap set to the seats bought, and is sold at a discount. The sign-in is personal and never names an organization: the tie is Clerk's invitation, an email with an organization-specific link the buyer sends from Clerk's hosted account portal. The server takes the higher of a person's own plan and their active organization's, so a site buys User seats and its hoster a Host license.
- **Where the license lives.** Public metadata on the Clerk user or organization, `License: { Plan, Until }` with `Seats` on an organization, written through the Backend API by our payment flow (the store's webhook, Promotion and Monetization's) and carried into every session token by the instance's session token template. The server reads one claim, signed by our instance, which nobody else can forge; a server is bound to nothing and counts nothing.
- **What the server enforces.** Three checks, each naming the plan it wants. At sign-in: the Administrator needs Host; a person placed in Owners or Members needs User; a Watcher-only or unplaced person is admitted free; a session below what its roles need is refused 401 with the error `license` and the plan, and the sign-in box says so with a link to the pricing page and Clerk's sign-out. At the settings: Scope Public is saved only from a session whose plan is Host, so a Local server goes Public from a signed-in licensed owner; a server configured Public from its file or environment starts and listens, since nobody is there to sign in before it starts, and admits licensed sign-ins alone. At a drag into Owners or Members: refused when the record's last-seen plan is below User (the plan is written on the record at each sign-in, and the user page shows it).
- **The Administrator of a fresh server.** When the settings name no AdminEmail, the first person to sign in on a Public server with a Host plan becomes the Administrator: their email is written to the settings and the start log says so. A Docker server may take CONSENSUS_ADMIN from the environment. The guide says to sign in before telling anyone the address.
- **Not now.** An LLM connection as a kind of Service account (a registry record of type llm with its activity page, the run still acting as its presser) was weighed and left for a step of its own under LLM Tasks.


## Where Clerk fits

- Clerk identifies **people on a server that listens beyond the machine**: every Public server, the customer's and ours, and Consensus-AI Cloud (Promotion and Monetization Step 6). It is the accounts, the sign-in, the password reset, the invitations and the multi-factor; Consensus manages no accounts or passwords of its own.
- Clerk never touches the **Free local tier**: a desktop or a headless server with Scope Local or None has no sign-in, a request is the owner, and it works with no network and no Clerk account. A Local server offers a sign-in in the Settings popup, for the owner who wants to go Public with a license; nothing is loaded from Clerk until it is asked for.
- Clerk is the **identity in front of the registry**, not the registry. Users.json is the server's list of users and their roles, each record keyed by the Clerk user id; the project role folders (Owners, Members, Service, Watchers) are Accounts and Roles' and the Admin is User Management's. Clerk's organization roles grant nothing in Consensus by themselves.
- Clerk authenticates **humans**. Agent sessions, the desktop's saved servers and a user's own scripts and services hold a token the user minted from their user page; a Service account's systems hold one the Administrator minted; a server LLM connection runs as the person who pressed the button, on a run-scoped token the server makes (User Management, LLM runs and agent sessions). Clerk's own machine credentials (API keys, M2M tokens) are a later option, not a dependency.
- There is **one instance**, ours. Its publishable key is built into the code, so a customer's server needs no Clerk section at all; the secret key and the webhook secret are our own servers', never a customer's. The section stays as an override for someone running their own instance, and for the tests.


## The Clerk application

The choices in the Clerk dashboard, made once, in this order:

- **Name:** Consensus-AI, the public name. The development instance is enough until the hosted tier exists; the production instance needs a domain we control and our own Google and GitHub OAuth applications.
- **Domain:** the hosted server is app.consensus-ai.liquicode.com, beside the docs, and the production instance's CNAME records (the front-end API, the accounts portal and the mail records) sit under consensus-ai.liquicode.com.
- **Identifier:** email address only. No phone number (paid in production, and SMS is a support burden), no username.
- **Sign-in:** email verification code, GitHub and Google. Passwords are off for new users: the audience is developers, and a code plus GitHub covers them without resets. Passkeys are left off until the production instance is paid.
- **Multi-factor:** off in development, a paid feature in production; a site may require it per organization later. Backup codes go on with it when it does.
- **Organizations:** on. One organization is one site license, a customer's team; personal accounts stay allowed so a single licensed person signs in without one. Membership is Clerk's: invitations, removals and the cap are the hosted account portal's, and the page makes a person's organization active at sign-in so the token carries its license. Who holds which role in which project stays Consensus's, in Users.json.
- **Session token template:** the custom claims every session token carries, so a server needs no secret key to know a person: `email`, `first`, `last` and `username` from the user, `license` from the user's public metadata and `org_license` from the active organization's.
- **Sign-up mode:** public in development; waitlist on production from the launch until the hosted tier takes customers; public after.
- **Sessions:** Clerk's defaults, one session per browser, no multi-session.
- **Billing:** Clerk Billing stays off. The License metadata is written by whichever store sells (Paddle or Lemon Squeezy, which handle tax, as Promotion and Monetization Step 4 says); Clerk Billing could write the same metadata later.
- **Webhooks:** user created, user updated, user deleted, organization created and organization membership created and deleted, pointed at our own servers' webhook route and signed with the webhook secret. A customer's server cannot be an endpoint in our instance; a person removed there stops at their next token refresh, within a minute.


## How it meets the code

- **Configuration.** The publishable key of our instance is a constant in `src/Clerk.js`. The optional `Clerk` section in consensus.json (the Settings popup) overrides it with another instance's publishable key, adds the secret key and the webhook secret on our own servers, and names the Administrator's email. On a Public server people sign in through the instance the key names; on a Local server the sign-in is optional and the owner's.
- **Identity.** A request is an account's token (Authorization: Bearer, looked up in Users.json under its account, a user's or a Service account's) or a Clerk session JWT in the same header, verified offline against the instance's public keys. On a Public server the subject is looked up as a Clerk user id; a subject the registry lacks is written from the token's claims (the template above), matched by email to a record the Administrator made by hand, else new with no role, and fetched from the Backend API only when a secret key is present and the claims lack an email. The license comes from the claims, the higher of the user's and the organization's, and is checked against what the person's roles need. On a Local server a session is the owner's: the owner record takes the Clerk id and the plan, and a bare request stays the owner.
- **The page.** No React: the page loads the vanilla ClerkJS script from Clerk's CDN with the publishable key when the server requires a sign-in, when a sign-in is remembered, or when the Settings popup's Sign in button asks; mounts Clerk's sign-in box in a popup when the API answers 401, with the license message and the pricing link when the error is `license`; and mounts the user button in the title bar. The page asks Clerk for the session token before each API call; Clerk refreshes it in the background. Sign out is Clerk's. The popup's Public choice is enabled by a Host plan on the session.
- **The server.** One module, `src/Clerk.js`: the JWT verification, the person and the license from the claims, the webhook signature check, and the registry writes the webhooks cause. The route is `POST /api/clerk/webhook`, unauthenticated, verified by its signature. No dependency: the verification is Node's crypto.
- **Agents and the desktop.** As User Management says: the agent session holds a token the person minted on their user page (Create token, Revoke), the desktop's saved servers hold one each, and a server connection runs as its presser. A person needs such a token because Clerk's session tokens live a minute and only a browser refreshes them. The desktop's own server signs in like the browser (Step 7): the page's own server is the browser's one root or the desktop's own under /servers/local, the desktop's page server forwards the window's host so the token's azp still matches, and the page server's port is remembered so the sign-in survives a restart; the desktop's saved servers stay on tokens. The production instance needs http://127.0.0.1 and http://localhost among its allowed origins for the desktop (Step 6).
- **Organizations and projects.** An organization is a site license, not a server and not a project. The server never holds one; a member's token carries the organization's license, and the Administrator or a project Owner places the person in the role folders as before.


## Limits and prices

As read on 2026-10-18, to be checked on clerk.com/pricing before the production step: Clerk's free tier covers 50,000 monthly retained users since February 2026, with Pro at 25 dollars a month. Older write-ups put the free tier at 100 active organizations of 5 members each, and 1 dollar an organization beyond that on Pro; a Clerk member cap matters only if it falls below what a customer's team needs, and is then our Clerk plan to raise. Phone numbers, passkeys and multi-factor are paid in production. Promotion and Monetization Steps 4 and 5 were brought onto the license model above on 2026-10-21 (its reconciliation thread): User, Host and Site licenses sold through the store, whose webhook writes the License metadata; managed runs through a relay of ours; the free image counts nothing.


## Out of scope

- Enterprise SSO (SAML and OIDC through Clerk's enterprise connections): a step of its own when a customer asks.
- Clerk Billing, Clerk API keys and M2M tokens: noted above as later options.
- The hosted tier's provisioning (one server per customer): Promotion and Monetization Step 6.


## Steps

1. **The Clerk application.** The development instance made with the choices above, the keys kept out of the repository. No code.
2. **Verification** (User Management Step 4 starts here). `src/Clerk.js` and the `Clerk` settings section: a Clerk JWT identifies a registered user; tests over a signed test token.
3. **The page.** ClerkJS loaded when the server says Clerk is on; sign-in, user button, the token on each call; the Ui smoke against the development instance.
4. **The registry follows Clerk.** The webhook route and the registry writes; the organization membership mapped onto the registry.
5. **The license.** The model of the section above: the built-in publishable key and the section as an override; the person and the license from the token's claims; the trusted network removed; the three checks (sign-in, Scope Public, the drag) by plan rank, Host over User, Watchers free; the first Host sign-in the Administrator; the sign-in offered on a Local server from the Settings popup, loaded only when asked; the license message in the sign-in box; the tests and the docs. *Decided before the build (2026-10-20, the license thread): the twelve points as recommended, with the owner's changes: the Users fold stays on a Local server with the owner's tokens and the Service accounts; Public needs a licensed sign-in to be saved; the license kinds Host and User; LLMs as Service accounts left for later.*
6. **Production.** The production instance under consensus-ai.liquicode.com, our own OAuth applications, the mail records, waitlist mode; the built-in key swapped to the production instance's; the session token template and the License metadata on the production instance; the desktop's origins (http://127.0.0.1 and http://localhost) among the allowed origins; a pricing page on the docs site; the guide page updated.
7. **The sign-in everywhere.** However Consensus is run, a person signed in with a Host license can set the Scope to Public and anyone else gets Local and None: the desktop's own server gets the browser's Sign in button and rule (the one thing to build; node, npm and npx had it from Step 5; a Docker or file-configured Public server listens and waits for a licensed sign-in); the desktop smoke checks the button, the greyed-out Public and that nothing is loaded from Clerk until asked; a real sign-in in the desktop window is a case of the Clerk browser smoke. *Decided before the build (2026-10-20, the sign-in everywhere thread, resolved with no reply).*
