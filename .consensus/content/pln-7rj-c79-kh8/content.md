# Installer

A Windows installer for Consensus Desktop, built with electron-builder from the repository root. The build and the icon exist since 2026-10-14 (commit 74b1b83, "Installer: the icon"); this plan records what is built and what remains before the installer can be handed to someone else. The plan stays a Draft until the signing is done.

## What is built

- `npm run dist` runs `electron-builder --win nsis` from the root; the configuration is the `build` block of the root package.json, so the server, the public page and the production dependencies ride along with the desktop.
    - The root `main` stays the server (src/Server.js); the builder's `extraMetadata.main` names desktop/main.js as the app's entry, so the npm package and the CLI are unchanged.
    - The app archive (resources/app.asar) holds `desktop`, `src`, `public`, `.guides/build-with-consensus.md` (the server reads it for /instructions) and package.json, plus the production `node_modules`. Dev dependencies, `bin`, `docs`, `test`, the dot folders and the tilde folders stay out.
    - The vendor files (angular, bootstrap, marked) are served from where `require` resolves them, which works inside the archive.
- Output goes to `~dist` (excluded from source control by the tilde rule):
    - `Consensus-Setup-<version>.exe` (the `artifactName` setting, no spaces, so the download link is plain; 2026-10-14): the NSIS installer, about 121 MB; not one-click, the install folder can be chosen, per-user install.
    - `win-unpacked/`: the installed layout, runnable as is for a smoke.
    - `latest.yml` and the `.blockmap`: what electron-updater would read; unused for now.
- The version on the installer is the root package.json version.
- The installed app behaves as the checkout's `npm run desktop`: it reads `<user>/.consensus/consensus.json`, starts its own server from it on port 3500, and keeps its settings there. The app archive is read only, so nothing may be written next to the code; nothing is today.
- desktop/main.js's "new window" spawn passes the app folder only from the checkout: installed, the executable is the app, and the folder would have been read as a project argument.
- Smoked on 2026-10-14: the unpacked executable launched on a temporary config and user-data folder with `--port 0`, showed the Consensus page with Angular loaded, served the vendor files and the stylesheet from the archive, and created a fresh config and projects folder.
- Icon. Built 2026-10-14. The build no longer warns, and the installer, the executable and the taskbar show the Consensus mark.
    - The brand already existed: the docs' mark, `docs/images/mark.svg`, a ring open at the top right with a check inside, stroked in the page's accent color (#0d6efd) on a transparent ground, no text. It is the one branding image; the speech bubbles proposed earlier are dropped. The master is `public/img/mark.svg`, the same drawing, served by the web server and the desktop; the docs keep their copy because the docs folder is published as it is.
    - Derived from the master with ImageMagick (on the build machine; the project takes no image dependency) and committed: `desktop/icon.ico` with 16, 32, 48, 64, 128 and 256 pixels in one file, named in the `win.icon` setting, and `desktop/icon.png` at 512 pixels for a later Linux build. electron-builder makes the installer's and uninstaller's icons from the `.ico`. To render again, each size from the vector so the small ones are crisp:
        - `magick -background none -density <size * 96 / 64> public/img/mark.svg -resize <size>x<size> -depth 8 mark-<size>.png`
        - `magick mark-16.png mark-32.png mark-48.png mark-64.png mark-128.png mark-256.png desktop/icon.ico`
    - From the checkout (`npm run desktop`), desktop/main.js names `desktop/icon.ico` as the icon of the window (the servers screen and the page) and of a detached tab's window, so the title bar and the taskbar show the mark there too; the packaged executable carries its own. Checked by capturing the title bar of a launch on a temporary config.
    - No `.icns` yet: this ImageMagick cannot write one; it is made from the same renders when the Mac build comes.
    - The web page links the SVG as its favicon (`<link rel="icon" href="/img/mark.svg">`, in place of the empty data URL) and the About popup shows the mark before its title (`.about-mark` in consensus.css). The docs already link theirs.
    - Checked: the icon extracted from the built `Consensus.exe` and from `Consensus Setup 0.4.0.exe` is the mark; the running server serves `/img/mark.svg` and the page with the favicon; the test suite passes (179).

- Published (2026-10-14): a GitHub Release per version, tagged `v<version>` on the commit it is built from (v0.5.0 on fdc836d), with the installer, its blockmap and `latest.yml` attached; the docs link the releases page (https://github.com/mchiver/consensus-ai/releases/latest) from the landing page's installer card and the guide's "The installer" section, which also says the installer is unsigned and how SmartScreen is passed. The release is made with the GitHub CLI (`gh release create v<version> ~dist/Consensus-Setup-<version>.exe ...`) or on the releases page by hand.

- Open with Consensus (2026-10-17): the installer adds the entry to the file explorer's context menu of a folder and of a folder's background, each running `Consensus.exe` on that folder (that folder's project alone, as `consensus <path>` does; the app side existed since plan Run Shapes, Step 4). `build/installer.nsh`, named by `nsis.include`, writes the two keys under `Software\Classes\Directory` (`shell\Consensus` with `"%1"`, `Background\shell\Consensus` with `"%V"`; the label and the executable as the icon) through SHCTX, so the per-user install writes the current user's classes with no elevation and a per-machine install would write the machine's; the uninstaller deletes both. Windows 11 lists the entry under "Show more options", as it does every registry-made entry; the guide's installer section says so. No opt-out in the installer, and no entry on files.
    - Checked 2026-10-17: the installer rebuilt (`npm run dist`, no warning), installed silently per-user on the build machine; both keys read back as written; the installed executable run on a temporary config with a temporary folder as its project opened the page on that project alone, with the title bar, and made the folder's `.consensus`; the silent uninstall removed the executable and both keys.

## What needs to be done

- Signing. The build calls signtool with no certificate, so the installer is unsigned: Windows SmartScreen warns on first run ("Windows protected your PC") until the publisher is known. A publicly trusted code-signing certificate is needed, and since 2023 the CA/Browser Forum rules require its private key to live in hardware or a cloud key service, never in a file.
    - Decided (owner, 2026-10-14): Certum Code Signing in the Cloud, bought through SSLmentor (https://www.sslmentor.com/certum/certumcodecloud). Certum is the CA; the certificate and its key live in Certum's cloud HSM and are reached through SimplySign, so there is no token to ship and no key custody of ours. It is a certificate we own, usable with any signing tool and on any machine where SimplySign Desktop runs; nothing in the build moves to a cloud provider.
    - What it is, as of 2026-10-14:
        - Price at SSLmentor, excluding VAT: $177 for one year, $132 a year for two, $116 a year for three; the Individual Developer variant $115 a year for three years; EV in the cloud from $226 a year. A certificate is issued for at most 460 days, so a two or three year purchase is reissued once or twice along the way, at no charge.
        - Validation: OV checks the organization in the company register and its address, and the admin contact passes an online identity check (an ID document and a face scan). The Individual Developer variant checks the person's ID and a utility bill for the address. Two to four business days after the documents are in; no guaranteed time.
        - Signing: SimplySign Desktop (Windows) connects to the cloud with the account name and a one-time code from the SimplySign mobile app, and while connected the certificate shows in the Windows certificate store as if on a card. signtool then signs with the certificate's thumbprint (`/sha1 <thumbprint> /fd sha256 /tr http://time.certum.pl /td sha256`). The connection needs the code each time, so signing happens on a machine where someone is present; it is not a CI step.
        - SmartScreen: reputation accrues as signed installs are seen; Microsoft stopped giving EV certificates instant reputation in 2024, so the OV certificate is the right buy.
    - In the build: electron-builder signs through signtool with the certificate picked from the store, `win.signtoolOptions` with `certificateSha1` (the thumbprint), `rfc3161TimeStampServer` `http://time.certum.pl`, `signingHashAlgorithms` `["sha256"]` (no SHA-1 signature; Windows 7 is not a target) and `publisherName` as the certificate's subject, for the installer's check. No credential goes into the repository; the thumbprint is not a secret. `npm run dist` is run with SimplySign Desktop connected; without it signtool finds no certificate and the build fails rather than producing an unsigned installer.
    - Steps, the owner's side first, then the build's:
        1. Owner: order the certificate at SSLmentor (OV, or Individual Developer if the publisher is the person rather than a company; the publisher name on the SmartScreen prompt is what is validated), pass the validation, and activate it on SimplySign; install SimplySign Desktop on the build machine and the mobile app on the phone.
        2. Owner: connect SimplySign Desktop once, open certmgr.msc, and read the certificate's thumbprint and subject.
        3. Build: the four values into the `win.signtoolOptions` block of package.json; `npm run dist` with SimplySign connected; `signtool verify /pa /v` on the installer; the signed installer checked on a clean machine for the publisher name on the SmartScreen prompt. Then this plan goes to Plan and, after the check, Finished.
    - For the record, the two cloud providers compared before the decision: AWS has no service that issues publicly trusted code-signing certificates (Certificate Manager is TLS only, Private CA is not trusted by Windows, Signer needs an importable key the CAs no longer give); it could only hold a KMS key for a certificate bought elsewhere, signed through Jsign. Azure Trusted Signing is Microsoft as the CA at $9.99 a month, supported natively by electron-builder through `win.azureSignOptions`, with an Entra app registration and the identity validation's known friction. Certum sits between: a certificate of our own at a comparable yearly price, with a vendor's signing client instead of a cloud account.
- Out of scope for this plan, noted for later:
    - Auto update with electron-updater over GitHub Releases: the build already writes `latest.yml` and the blockmap; it needs a `publish` setting, a release workflow and the signing above, since an unsigned update is refused.
    - Mac (`.dmg`, needs notarization) and Linux (AppImage, `.deb`) targets: the same config with `mac` and `linux` blocks, built on each platform; the 512 PNG is ready for Linux; the `.icns` is still to be made.
    - A `README` note on where the installer is downloaded from and that the installed app runs its own server on port 3500.
