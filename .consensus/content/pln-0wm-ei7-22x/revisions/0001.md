# Corpus File Inclusion

> Files over the size limit, or not text, are listed but not read, as zips are now.

**LLM:** **Drop `Corpus.Extensions`: `Include` and `Exclude` choose the files, and a file is read unless it is too large or binary.**

Today a file must also have an extension on the `Corpus.Extensions` list (in `context-server.json`, and in `consensus.json` for zips) before it is read and indexed. With `Include` and `Exclude` on each corpus, that list repeats what they can say (`Include: [ "**/*.md", "**/*.js" ]`), and it shuts out files with no extension: in the "Consensus" corpus, `.gitignore` is listed but not read, and `LICENSE` or `Dockerfile` would be too.

Proposed:

- **Context server:** `Extensions` goes. Every file the corpus lets in (`Include`, `Exclude`, the `.gitignore` files) is read and indexed, unless it is larger than `MaxFileKilobytes` or binary (it holds a NUL byte, as images, archives and executables do). Such a file is still listed, with its reason.
- **`MaxFileKilobytes` stays**, as a guard: it keeps a large generated file (`package-lock.json`, a bundle) out of the index by accident. Minified or generated text under the limit gets in unless `Exclude` names it: that is the trade for one rule.
- An `Extensions` key left in an existing settings file is ignored, and the server says so once at start.

One question, with my recommendation:

- **Uploaded zips in Consensus.** A zip has no `Include` or `Exclude`, so today `Extensions` is the only thing choosing its files. Recommendation: the same rule for zips (read unless too large or binary), and `Extensions` goes from `consensus.json` too, so both servers read files the same way. The other choice keeps `Extensions` for zips only.
