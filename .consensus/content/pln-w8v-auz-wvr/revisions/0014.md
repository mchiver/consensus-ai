# Run Shapes

Consensus is deployed through a command line invocation.


## Current Implementation

The following command line arguments are curtrently supported:
- `--data <folder>`: the data folder; ~data beside the checkout by default
- `--port <port>`:  the port to listen on; the settings' Port, else 3500
- `--host <address>`: the address to listen on; the settings' Host, else 127.0.0.1; 0.0.0.0 for every interface
- `--help, -h`: prints the usage line and exits


## Proposed Changes

Consensus always loads its global config from the system's user folder `<user>/.consensus/consensus.json`.

The global config contains:

    - global settings
        - Server name
        - listen address and port
    - list of local LLMs
        - Name: the participant it posts as, <connection>@<server name>, for example
          claude-cli@cube12 or ollama-kimi-k2.6:cloud@cube4; every reply and result records it
        - Type, etc.
    - list of local Projects
        - local path
        - filters, etc.
    - list of servers
        - connection info
        - last view settings

Scope, in the global config: None (the local API server is never started; the desktop is a client of the saved servers only, and has no local projects), Local (it listens on 127.0.0.1, for this machine's desktop), Public (it listens on 0.0.0.0, for remote connections); Scope replaces Host. The desktop's tree shows every connected server as a root, the local one first when it runs, with its projects as children; the page's API calls go to the root's server. Each server keeps its own participants and tokens. The multi-root tree is the plan's last step.

A Consensus server serves a number of configured Projects and LLMs.

The server runs the LLM runs (Review, Build, Session). A client, the desktop window or a browser, asks the server for a run, and the server starts the command or calls Ollama, as the desktop does today; the code for the runs moves from the desktop into the server. The server still reads no code on its own: a run does, over the project's folder, as a tool of the model. An LLM works only on the projects of its own machine: the tools assume the project's folder is locally accessible, so a run is never asked of a remote server's project.

Each Project is tied directly to a locally accessible folder.
This folder serves as the context for all project plans and LLM interaction: a Project is what a workspace was, and the two merge. The global config holds the folder's path, which is this machine's; `.consensus/project.json` holds the Include, Exclude and Commands, which travel with the folder. A Project made in the UI needs a folder from now on: the desktop asks for one, offering `<config>/projects/<name>/`, and a headless server makes that default folder. A folder opened with `consensus .` or `--project` is added to the global list, so a bare `consensus` shows it next time.
This folder contains a `.consensus` subfoider which stores:

- `project.json`: the project's tree, its Include, Exclude and Commands, and the ids of its archived items
- `content/<id>/content.md`: an item's text; `content.json` its record; `threads.json` its threads; `revisions/` its revisions; and any file that belongs to it
- `archive/<id>/`: an archived item, moved whole. A finished plan is moved there with Archive in its menu and brought back with Restore; the archive shows as a folder at the bottom of the project, folded, below the tree, and its plans open read-only until restored.
- `trash/<id>/`: a deleted item, moved whole

if a `.consensus` folder does not exist, one is created and initialized.


### Command Line Arguments

- The CLI takes an optional `<path>` parameter which is a path to a project root. When this is provided, then it has the same behavior as the `--project` argument below.

- `--config <folder>`: Global config path. Defaults to the system's user folder `<user>/.consensus`. The Docker image runs `--config /data --headless`, so the global config and the projects it makes (under `/data/projects/<name>/` by default) live in the volume; `compose.yaml` and the Getting started page change with it. `--data` stays accepted for one release as an alias of `--config`, so an existing data folder is found and migrated at first start.
- `--project <folder>`: opens an instance on that project alone, the way VS Code opens a folder: the tree shows that project and nothing else, no other configured project and no remote server, and the folder joins the global list as a recent project; its `.consensus` is created when missing. Run with no path, the desktop shows everything the global config has. A second instance opened at the same time takes a free port when the configured one is taken, so two folders can be open at once, each in its own window. This is the way to hold an ad-hoc session in a local folder.
- `--port <port>`:  Port to listen on; the settings' Port. Defaults to 3500.
- `--host <address>`: Address to listen on; the settings' Host. Defaults to 127.0.0.1; 0.0.0.0 for every interface
- `--headless`: Skips the UI and just runs the api server. Two entry points share one start module: the packaged desktop executable is `consensus`, which starts the server and opens the window, or no window with `--headless`; `bin/consensus.js` is the headless form for a plain node install and the Docker image, which has no Electron, taking the same arguments and refusing the UI ones with a message (`--headless` is accepted there and does nothing).


### Initialization Sequence

- Loads global config from `<user>/.consensus`.
- Run the api server at `<host>:<port>`.
- Load and mount local LLMs.
- Load and mount local Projects. If `--project` is used, then load only the specified project.
- Run desktop UI against this consensus server. if `--headless` is used, output to console and skip the UI. The server serves the page to the window and to a browser alike. There is one page again: public/ is live and desktop/page/ goes; the desktop keeps only what needs the window (the folder picker, the native theme).


## Invocation Scenarios

**Run Without Arguments**

```shell
consensus
```

Loads everything found in `<user>/.consensus`.
The project tree contains all local LLMs and Projects.
The desktop UI is run.


**Run "Here"**

```shell
consensus .
```

Loads settings and LLMs from `<user>/.consensus`.
Loads the Project found in the current working directory.
If the current working directory does not have a `.consensus` folder, then one is created and initialized.
The project tree contains all local LLMs and the loaded Project. Other Projects found in the global config are not loaded.
The desktop UI is run.


**Run on a Single Project**

```shell
consensus /projects/tic-tac-toe
```
or
```shell
consensus --project /projects/tic-tac-toe
```

Loads settings and LLMs from `<user>/.consensus`.
Loads the Project found at the given path.
If the path does not have a `.consensus` folder, then one is created and initialized.
The project tree contains all local LLMs and the tic-tac-toe Project. Other Projects found in the global config are not loaded.
The desktop UI is run.


**Run a Server**

```shell
consensus /projects/tic-tac-toe --headless
```

Same behavior as **Run on a Single Project** with the exception that the desktop UI is never run.
