# Step 1: Scaffold and Threads

The first step of plan UI Components: the component scaffold and the first extraction, Item Thread Filters and Item Threads (items 6 and 7 of the parent). The app behaves as before, except where a decision below says otherwise.

## The scaffold

A component is an AngularJS .component(), one folder per component under public/components/<name>/, holding <name>.js (the registration and its controller), <name>.html (the template, loaded by templateUrl, no build step) and <name>.css (its styles, one link tag each; consensus.css keeps the page, the palette and the shared classes). index.html becomes a skeleton of component tags. A component takes what it shows through bindings or the State service, reports through events, and its header comment names both: that is its interface. Names follow the CLAUDE.md exception: Angular's camelCase at registration, kebab-case tags, one-word bindings where possible, nothing else camelCase.

## Item Thread Filters

The "Waiting on ..." and "Highlight ..." dropdowns above the thread list. Changes are broadcast to the other components (the Html and CodeMirror views, the thread list) so they update their thread displays. Filters are global and apply to all items, not just the selected one.

Decided: the Waiting-on filter becomes global like Highlight, remembered in the browser, and the per-tab Filter goes (the guide's Tabs section changes with it). A change is a State event (highlight-changed, and a new filter-changed) that the html-view, the CodeMirror editor and the thread list listen to. The dropdowns are a thread-filters component and stay above the thread list.

## Item Threads

The list of thread cards according to the Thread Filters. Each card has components within it:

1. Thread Header: thread name, state, waiting on, anchor text, and delete.
2. Thread Transcript: the transcript of thread messages with owners and timestamps, rendered markdown as an Html view.
3. Thread Actions: a text input box and buttons for Replying, Resolving, etc.

Decided: the reply box and the compose box are an editor of the kind the Editor setting names, Monaco or CodeMirror, in a plain mode: markdown, word wrap, no line numbers, no anchors, no preview, no save. Five lines high to start, with a drag handle on the bottom edge; the dragged height is remembered in the browser, one height for both boxes. One instance per place, mounted when its box appears: one for the reply form (shown on the selected thread only) and one for the compose card. The reply draft stays kept per thread (State.Drafts). The compose card is a thread-compose component of its own, beside thread-card with its thread-header, thread-transcript and thread-actions; the inline delete confirmation stays in the header, the collapse controls in the transcript.

Until Step 3 adds CodeMirror and the Editor setting, the box is Monaco.
