# Printing and Reporting

There are times when a plan, its Subplans and all their threads should be flattened into one coherent document, for reporting, review and printing: a record of everything done on both sides, the owner's and the LLM's. This plan says what that document holds, how it is made, and how it reaches paper or a PDF. It rests on the owner's four statements and one of the project's:

1. The report is a record of both sides: every thread, every reply, who wrote it and when, and what became of it.
2. It holds the final revision of each plan only. The revision history stays in the app.
3. It renders to a PDF file.
4. Every owner and timestamp is shown: the author and time of each reply, each resolve and each apply, and the plan's own dates.
5. No new dependency. The project has marked on the server for markdown, a browser in front of every user, and Electron in the desktop; the PDF is the browser's print of a page made for printing.

The build is three steps, each a subplan designed before it is built: the report itself as a page the server serves, the way to it from the app, and the PDF.


## The report

One document per plan, composed on the server as markdown and rendered to HTML, in this order:

- **The title page.** The plan's title, its state, its project and folder path, the server's name, when the plan was created and last updated, the participants who took part, the counts of threads by status, and the date the report was made.
- **The text.** The plan's final revision, rendered as the Read view renders it, with each anchored passage marked and numbered in the margin so the threads below can be found in it.
- **The threads**, in the order of their anchors in the text, whole-document threads first: the number, the anchor's words quoted (or "the whole document"), the status, then every reply with its author and timestamp, then the records: resolved by whom and when, applied by whom, when, at which revision, with the outcome. A reopened thread says so; a detached thread quotes the words it had.
- **The Subplans**, each the same way (title page reduced to a heading with the dates and counts, text, threads), nested in the tree's order and depth, so a plan with Subplans reads as chapters.

What stays out: the revision history, deleted threads, the Context folder's documents, the trash, the archive unless the plan itself is archived (then it reports as it is). Participants appear by their display names, with the participant name once on the title page.


## Step 1: The report page

`GET /api/plans/:id/report` answers the report as HTML: a complete page, no AngularJS, the site's fonts and the Read view's markdown styles inlined, a print stylesheet (page breaks before each Subplan, the title page alone, no running controls, the margin numbers kept, black on white whatever the app's theme) and one row of controls at the top that the print leaves out: Print, and the theme toggle for reading on screen. `GET /api/plans/:id/report.md` answers the same report as markdown, for an agent that wants the flattened plan as context or to keep it with the source. The route is the owner's, the llm's and a member's alike: it reads what they could read. A document has no threads and is refused with 400; a plan in the trash 404.

The composition is one module, `src/Report.js`: `Compose( Store, PlanId )` returns the markdown, `Render( Markdown )` the HTML, both pure over what the store gives, tested in `test/Report.test.js` over a seeded project (a plan with Subplans, anchored and whole-document threads, one reopened, one detached, one deleted) by checking the markdown's sections and the HTML's marks. The anchors are placed with `src/Anchors.js` as the page places them, so the numbering agrees with what the Read view shows. The guide's API page and `.guides/build-with-consensus.md` list the two routes.


## Step 2: Report in the app

A plan's row menu and the heading's menu get **Report** (after Export), and so does a Subplan's. In a browser it opens `/api/plans/<id>/report` in a new tab; in the desktop it opens it in a new window of the app, the page served through the root's forwarder as the instructions page is. The heading's Report is also Ctrl+P, listed in Help > Hotkeys. On a document the entry is absent. The Ui smoke opens a report from the menu and checks its title, its thread count and the first anchor's number.


## Step 3: The PDF

The Print button on the report page calls the browser's print. In a browser that is the print dialog, whose destination list has Save as PDF, and the print stylesheet makes the result the document above. In the desktop the button asks the window to print to PDF instead: `webContents.printToPDF` with the save dialog, the file named after the plan (`<title>.pdf`), a toast when it is written, the folder remembered in the config's `Remembered`. The server itself makes no PDF: the Docker image has no browser, and a browser is in front of everyone who wants one. If a server-side PDF is wanted later (a run that files a report, a nightly archive), it is a plan of its own over the headless driver the tests already have.


## Decided before the build

The decisions below are the plan's defaults; the thread on this plan lists the ones that are the owner's.

- The report includes every thread whatever its status, contested ones marked as such: a report of work in progress is still a record. Deleted threads are left out, as their text is gone; a revision record that names one says "(deleted thread)" as the app does.
- The markdown form is served beside the HTML because it costs nothing and gives an agent the flattened plan.
- Timestamps are written in full (date and time, the server's zone named once on the title page), never relative.
- The PDF is the browser's or Electron's print; no server-side PDF in this plan.
