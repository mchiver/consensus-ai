# The Server

Two applications, reframed by the owner on 2026-10-26 after plan Rearchitecturation (pln-gkn-zlj-42q) was built: the **Desktop**, which works over a local folder in sidecar mode and, once signed in, connects to Servers as a thin client; and the **Server**, a superset of the Desktop that adds the management of a machine's resources on top of project interaction. This plan sets out the distinction between the two and the permissions each license level grants.

## Licenses

- **Unlicensed** (no sign-in): the Desktop in sidecar mode.
- **Registered** (free, signed in): adds connecting the Desktop to Servers, local and remote. A Registered user cannot run the Server.
- **Personal** ($5): adds running the Server to manage its resources, listening on localhost.
- **Professional** ($10): runs the Server listening on public addresses.

Each level includes the ones above it.

## Desktop: sidecar mode

The Desktop opens over a local folder and works in sidecar mode: the LLM session is the sidecar to Consensus. In sidecar mode the Desktop does not use a Server for anything, so there is no user management and there are no LLM Tasks. All of it works without a sign-in.

## Desktop: client mode

Once a user holds a license and signs in, the Desktop works as a thin client: it connects, through Connect to Server (formerly Connect to Host), to projects hosted on a Server and uses that Server's resources, invoking the LLM Tasks the Server offers. LLM Tasks always run on the Server.

## Sign-in

A user who signs in through the Desktop or the Server becomes the current user on that machine, a record stored in `~/.consensus/`. One user is signed in on a machine at a time, so a later sign-in signs out the current user. A sign-in replaces the current user, never the Administrator; the current user has the Administrator's functions when they are the Administrator.

User management is by email: a remote user signs in with Clerk and passes the result to the Server, which validates the email against its roles, Administrator, Manager and Member; the Administrator record keeps the user's details and is matched by email. The Server runs under the authority of the Administrator: it takes its level from the current user's license, and runs at the Personal or Professional level only while the current user is the Administrator. A running Server keeps its level until it is quit. Later runs of either application use the current user as the user of record until a sign-out, or until the stored token expires.

## The Server

The Server stays as it is today: a single-instance application that adds management on top of project interaction. It is where these happen:

- user management;
- LLM management;
- LLM Task configuration and permissions;
- project management and permissions.

Management lives in the Server's window and in its web page, shown to the Administrator and the Managers only; there is no separate management address.

The first user to sign in to the Server with a Personal or Professional license is its Administrator, recorded in the Server's configuration; sign-ins to the Desktop do not count. Only the Administrator assigns Managers. Managers manage every part of the Server except assigning Managers.

Closing the Server's window does not end the application: a tray icon, or a minimized icon where there is no tray, restores the window, and its Quit ends the Server.

## Installation

The Desktop and the Server are distinct Electron applications that share components. They are installed and started separately. On the command line, `consensus-desktop [<folder> | --connect <name>]` starts the Desktop and `consensus-server [--config <folder>] [--port] [--scope]` starts the Server; `--headless` runs the Server with no window, which is what the Docker image and `npm start` run, and `consensus serve` stays its alias for a plain node install.

## What this changes

- The Server keeps project interaction, the editor and the threads included; the manager-only window of the earlier draft is dropped.
- The tiers of Rearchitecturation Step 6 move: the thin client goes from Personal down to Registered, the LLM Tasks leave the Desktop and run on a Server only, and Personal becomes running the Server on localhost.
- The dependency is inverted: the Desktop no longer starts, opens or stops a Server (Start, Open and Stop the Server Host leave its menus), and the Server offers Open in Consensus on any project it hosts, opening that project in the Desktop.
- The Desktop no longer reads the Server's consensus.json for the LLM connections and tasks.
- The Administrator and Managers replace "the Professional license holder is the Administrator".

## Steps

1. **The current user and the tiers.** The machine's sign-in moves out of the Desktop's desktop.json into a record in `~/.consensus/` (user.json: Email, Clerk id, Display, Plan, Until, Checked), read and written by both applications; desktop.json keeps only the Desktop's window settings. A sign-in writes it whole, replacing whoever was there; Sign out removes it. The record holds the license for 14 days from its last check against Clerk. The tiers become four, Unlicensed, Registered, Personal and Professional: Registered is a sign-in whose token carries no license, so Clerk needs no change. desktop/License.js moves to src/License.js, shared by both applications. Tests for the record and the tiers.
2. **The Administrator and the Managers.** The Administrator stays the settings' AdminEmail, now set by the first sign-in to the Server with a Personal or Professional license (Professional alone today). Managers are a list of emails in the settings, assigned by the Administrator alone. Everyone else the Server knows is a Member, given roles project by project as today. The Server's routes split in two: management, open to the Administrator and the Managers, and assigning Managers, the Administrator's. The Server takes its level from the current user's license while the current user is the Administrator; when the current user is anyone else, it does not start, and says whose sign-in it needs. Tests in Api, Operations and Users.
3. **The Server application.** A server folder beside desktop: the Electron main process running the server in-process over every registered project, its window on the page with the management parts open to the Administrator and the Managers, one instance per machine, a tray icon (or minimized icon) restoring the window and its Quit ending the Server. Open in Consensus on each hosted project row opens that project in the Desktop. `consensus-server` on the command line, with `--headless` for no window and `consensus serve` as its alias; the headless form reads the same record from its config folder. Its installer, Consensus Server, is built by `npm run dist` beside Consensus Desktop from one package.json. A Server test like the Desktop's, and the smoke.
4. **The Desktop's split.** Off the Desktop: Start, Open and Stop the Server Host, desktop/Host.js, the routing of mounted folders, the reading of consensus.json for the connections and tasks, and, in sidecar mode, the LLM page, the task buttons, the Users fold and the roles folders. Connect to Host becomes Connect to Server, open to Registered and above; in client mode the LLM Tasks are the Server's. The Desktop test and the smoke follow.
5. **The guide.** The Server page of the guide rewritten for the application, Getting started, the features page, the pricing page with the Registered tier, the readme and the pictures.
