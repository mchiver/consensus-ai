# Promotion and Monetization

Consensus is at 0.5.1: MIT licensed, local-first, a desktop application and a Docker image, documented publicly as Consensus-AI, with signed installers waiting on a certificate. Nobody outside this project uses it yet. This plan says how it gets seen, where it is distributed, what stays free, what is sold, and in what order. It rests on five statements:

1. The pitch is one sentence: *work the plan through with your AI, thread by thread, before any code is written.* Everything public leads with the loop (write, the agent comments in threads, resolve, apply, a revision trail), not with the feature list.
2. The audience is people who already code with agents: Claude Code, Codex and Cursor users, solo developers first, small teams second. Consensus is distributed where they already are, inside the agent ecosystem, not on a landing page they have to find.
3. The core stays MIT and free for a single user on their own machine with their own API key. Money comes from the licenses people hold: a User license for an Owner or a Member on any shared server, which is also the solo professional's commercial desktop license; a Host license to run a shared server; a Site license for a team; then from LLM runs performed on our key, and from hosting and support.
4. Nothing is sold before the server knows who is calling. That is met: since Clerk Step 5 a Public server admits a Consensus-AI sign-in or an account's token and nothing else, and reads the person's license from their sign-in; only Clerk Step 6, the production instance, stands before the first sale.
5. Revenue comes in the order of least infrastructure first: the per-person licenses, then managed runs, then hosting. Services (support, workshops) run alongside from the start.

The steps below are in order. Steps 1 to 3 cost no infrastructure and start now; Step 4 is the first money and waits on Clerk Step 6 alone; Steps 5 and 6 follow. Steps 4 to 6 were brought onto the per-person license model on 2026-10-21 (the reconciliation thread, resolved with no reply).


## The name

Consensus is also a funded research search product (consensus.app), so the bare name is not ours in search results or as a trademark. The public name stays **Consensus-AI** in docs, listings and the installer, with Consensus in prose, as the docs do today. Before Step 3 we check the trademark registers for Consensus-AI in software, and the handles (npm, GitHub organization, Docker Hub, X, Bluesky, Discord). If any of these fails, the name is changed before the launch, not after; a rename later costs every link and listing.

Whatever the check says, the docs carry a short disambiguation paragraph, on the landing page and in Getting started, that names the other Consensus plainly ("Consensus-AI is not Consensus, the research search engine at consensus.app"), links to it, and says in one line what this one is. It is a defensive measure: it answers the confusion before it is raised, and it is on record that we made the distinction ourselves.


## Step 1: Ready to be seen

What a stranger meets in the first minute, done before any announcement:

- **The one sentence** from statement 1 at the top of the readme, the docs front page, the npm page and the desktop's About.
- **One recording**, 60 to 90 seconds, no voice-over needed: a plan is written, an agent session reads `/instructions` and posts anchored threads, the owner replies and resolves, the agent applies, the revision trail shows the change. A GIF of it in the readme, a video on the docs front page. Recorded with the smoke harness so it can be re-recorded after UI changes.
- **A public demo project**, read-only, at a stable URL under the docs: this project's own plans, with their threads and revisions, as they are. The demo folder under `docs/` is its seed. The story of building Consensus with Consensus is the best evidence the product works.
- **Starter plans**: a `Templates` folder in a new project, holding an RFC, an architecture decision record, a design document, a sprint plan and a build plan with steps, each a short plan with the headings and a line on how to work it. New Plan offers them. They are also pages in the docs guide, one each, because each is a search query.
- **A changelog** at `CHANGELOG.md` and a Releases page on GitHub, with one line per plan finished, from the Finished folder backwards.


## Step 2: Distribution

Where it is installed from, each a listing that brings its own traffic:

- **`npx consensus-ai <folder>`**: the npm package, published, so the headless server is one line in any repository. The `bin` already exists; the package gets the public name, the readme and the keywords.
- **The Docker image** on Docker Hub and GHCR under the public name, with the compose file in the readme.
- **A Claude Code plugin** that carries the `build-with-consensus` guide as a skill and the "your turn in Consensus" workflow, so an agent session in any repository learns the API from the marketplace rather than from a curl. Listed in the plugin marketplace.
- **An MCP server** over the same API (`src/Mcp.js` or a separate small package), with the plan, thread, reply and apply routes as tools, so Codex, Cursor and the desktop's local models reach Consensus the same way. Listed in the MCP registries.
- **Package managers for the desktop**: winget and scoop on Windows, Homebrew cask on the Mac, an AppImage and a `.deb` on Linux, once the installers are signed (plan Installer).
- **Awesome lists**: awesome-claude-code, awesome-mcp-servers, awesome-ai-tools, with the one sentence and the GIF.


## Step 3: Launch

Posted in one week, each with the recording and a link to the demo project:

- **Show HN** on a Tuesday morning US time, the title plain: "Show HN: Consensus-AI, work a plan through with your AI before writing code". The first comment is ours: why threads and not chat, what is local, what is MIT.
- **Product Hunt** two days later, with the same assets.
- **Communities**: r/ClaudeAI, r/ExperiencedDevs, r/LocalLLaMA (for the local models), Lobsters, the Claude Developers Discord, the Cursor forum. Each post is written for that place, not cross-posted.
- **The Anthropic developer showcase** and a "built with Claude" write-up.
- **Content, monthly after the launch**: a write-up of one feature argued out with an agent, with the plan, its threads and the build log shown as they are. The first three: Run Shapes, Markdown Editor, and this plan. Published on the docs site under `/blog`, syndicated to dev.to and Hacker News.
- **A Discord server** and GitHub Discussions, linked from About, with a `good first issue` label on a dozen small items the day of the launch.

What counts: stars, npm and Docker pulls, desktop downloads, Discord members, and the number of public repositories with a `.consensus` folder (a GitHub code search), checked weekly in a document in the Context folder.


## Step 4: The paid line

The licenses, stated once, and the rule for which side of the line a feature falls on: a single person on their own machine with their own key pays nothing; a shared server, a seat on one, or work our servers do for you is paid. A license belongs to a person, not to a server (plan Clerk, The license): it is the `License: { Plan, Until }` public metadata on the person's Consensus-AI account, or on their organization, carried into every session token and read by the server at sign-in, at the Scope and at the drag into a role. A server is bound to nothing and counts nothing.

| Plan | Price | What it holds |
|---|---|---|
| Free | 0 | The whole application on a Local server: no sign-in, any number of installations, own API keys, MIT |
| User | 10 a month, or 99 a year | An Owner or a Member on any Public server where the person holds an account; the commercial desktop license; a monthly quota of managed runs (Step 5) |
| Host | 25 a month, or 249 a year | Runs a Public server and is its Administrator; includes User |
| Site | 8 a seat a month, five seats at least | A Consensus-AI organization carrying User for its members, the seats being Clerk's membership cap; the hoster's Host license is bought beside it |
| Enterprise | by agreement | On-premises terms, SSO through Clerk's enterprise connections, support with an SLA, training |

The prices are a starting point to test against the first hundred users, not a decision; they are in US dollars. A Watcher needs an account and no license; a Service account is a token and has none.

**The commercial desktop ask.** Free is personal and evaluation use. Commercial use on a Local server asks for a User license after thirty days, Sublime style: the application never locks and counts nothing; About shows the license state, and once a week on start an unsigned-in server says that commercial use needs a User license, with the Sign in button and the pricing page. A session holding User or above silences it. There is no key and no module of its own: the check is the Local sign-in Clerk Step 5 built, reading the same claim.

**The store.** Licenses are sold through Lemon Squeezy or Paddle, which handle tax. The store's webhook lands in Consensus itself: `POST /api/store/webhook` in `src/Store.js`, verified by the store's signature, alive only on a server whose settings hold a `Store` section and the Clerk secret key, which is our own server (the docs host or the hosted tier's), never a customer's. On a sale it finds the Clerk user by the buyer's email, or creates one so that the invitation mail is Clerk's, and writes the License through the Backend API; for a Site license it creates the organization with the seats as its membership cap, writes the License on it and makes the buyer its admin; a renewal moves Until, a cancellation leaves Until to run out. The buyer signs in with the same email anywhere.

**The free Public server.** The Docker image and the headless server are free to download and run as Public servers, hold any number of accounts and count nothing. What a free team is short of is licenses: the Administrator needs Host and every Owner and Member a User license, while Watchers read and press the read-only tasks for nothing. That is how Clerk Step 5 is built.


## Step 5: Managed runs

Bring-your-own-key runs stay free and unlimited. A run on a Consensus key cannot be counted by the customer's server alone, since our provider key cannot live in a desktop, so managed runs go through a relay of ours: an LLM connection kind `Consensus-AI` in the Settings popup, pointed at the relay, whose credential is the person's session token (a Local server signs in for it, as it does for going Public). The relay reads the monthly quota from the claim, `License.Runs`, written by the store with the plan (so many runs a month on User, more on Host, pooled on a Site), counts the runs on our side, and refuses over the quota with a plain answer the toast shows; Settings shows the count. Metering by tokens, at the provider's price plus a margin, comes only when the quota is being hit, and is a step of its own then.

What the Team step promised before the license model is elsewhere: shared projects, accounts and roles are the Public server (plans User Management and Accounts and Roles); the Git sync of `.consensus` is Work's options (plan LLM Tasks); the audit log is each account's activity history; backups are the export; SSO and on-premises terms are Enterprise's, by agreement.


## Step 6: Hosted

Consensus-AI Cloud: a Public server run by us, one per customer, projects in a volume, the LLM connections on the customer's keys or on managed runs, billed per month with the Host license included; the customer's team signs in on its own User licenses or a Site's seats. It comes last because it carries the running cost and the on-call, and because by then the licenses have told us what the customers are. The desktop and the hosted server are the same program, so a customer moves between them with an export.


## Services and small money

From the launch on, independent of the steps:

- **Support contracts and on-premises licenses** for any company that asks, priced by agreement, with a page on the docs site that says so.
- **Workshops**: a half-day on planning with an agent, Consensus as the medium, for engineering teams. The template plans of Step 1 are the material.
- **GitHub Sponsors** linked from the readme, and a paid template pack (industry-specific plan sets) in the desktop's Templates, both expected to be small.


## Before any charge

What must be true before the first key is sold, in order:

1. Clerk Step 6 is done: the production instance under consensus-ai.liquicode.com, the session token template carrying the license, the License metadata the store writes, the pricing page; so a sale lands on an account every server can read.
2. The installers are signed (plan Installer), because a paid download that the OS warns about is a refund.
3. A privacy statement on the docs site: everything is local unless you turn on managed runs or sync; what leaves the machine, and to whom, is listed.
4. Opt-in telemetry, off by default, counting starts, plans, threads and runs, with the question asked once on first start, so the prices and the tiers can be tested against use.
5. Terms of sale and a refund policy on the docs site, written by a lawyer once; the store handles tax.


## Measures

The plan is working when, six months after the launch: a thousand GitHub stars, a hundred public repositories with a `.consensus` folder, a hundred User licenses sold, and five Site licenses. If the licenses do not come but the stars do, the price is wrong or the commercial ask is too soft, and Step 4 is revisited before Step 5 is started.
