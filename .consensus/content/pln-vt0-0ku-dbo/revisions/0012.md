# User Management

People besides the owner working on the same server, each as themselves, allowed per project what their role there allows. The owner's design of 2026-10-02 settled the role folders, the Users folder and the Admin; the rewrite of 2026-10-18 settled who the principals are: Clerk identifies people, Consensus manages roles and permissions, and an LLM is never a user. The subplan Clerk holds the sign-in; this plan holds the model, the registry, the roles, the tokens and the migration. The seven decisions of the rewrite were taken on 2026-10-18 (the decisions thread, resolved with no reply): trusted network for Public without Clerk, the person via the connection as a run's author, tokens until revoked, the owner's own named tokens on Local, the Admin by email, old names left in history, and Steps 1 and 2 first.


## The model

- **A person is the only principal.** Clerk says who they are, once, at sign-in. Consensus says what they may do, per project, through the role folders. Consensus keeps no passwords and no sign-in of its own.
- **An LLM is never a user.** A server LLM connection is a tool: a run is posted as the person who pressed the button, with the connection named in the record, so a thread reads as that person via Claude-CLI. The run is allowed what that person's role allows. An agent session is the same thing from outside: it holds a token a person minted, and acts as that person.
- **Scope decides whether identity is checked.** Local trusts the machine: no users, no sign-in, a request is the owner, as today. Public authenticates with Clerk when the settings hold a Clerk section; a Public server without one is a **trusted network**, where every request is the owner as today, and the Settings popup says so in plain words beside the Scope.
- **A token is the one credential for anything that is not a browser.** A token belongs to a person and has a name; a request carrying it is that person, via that name.


## Today

- The participants live in consensus.json, edited in the Settings popup: each has a Name (what threads and revisions record), a Display, a Role (owner, llm or member) and an optional Token. Only the owner resolves threads and writes the settings; only the llm applies; everyone else takes part.
- A request is identified by its token (Authorization: Bearer). A request with no token is the owner. The llm participant's token is served to whoever reads /instructions. Each LLM connection is a participant of its own with a token of its own (Run Shapes Step 3), and the agent session posts with one of those.
- cube4 listens beyond the machine: anyone who can reach it acts as the owner. This plan replaces the Owner Token the Readme named.


## Users

- A Public server with Clerk keeps a registry of its users in `Users.json` in the data folder, beside consensus.json. A user record is the Clerk user id, a login name (the Clerk username or the mail's local part), a display name, and the user's tokens. No credentials: Clerk holds those.
- A record is written when Clerk's webhook announces the user, or when a signed-in person reaches the server for the first time; it is removed when Clerk deletes the user, with its roles. A user with no role in any project sees the Users folder alone.
- The Users folder at the server level holds an item for each user; clicking one opens a tab page with the user's details, permissions (the projects and the role in each), tokens, and a history of activity on the server (the threads, replies, revisions and state changes by that user, read from the data, newest first). The Users folder is shown to every signed-in user; a user's page to the Admin and to that user.
- A Local server and a trusted-network server have no registry and no Users folder: the owner is everyone.


## Authorization

- Authorization is per project. A project has lists of **Owners**, **Members** and **Watchers**, as three role folders inside its own **Users** folder, a fixed folder after the Context folder, none of which is renamed, moved or deleted, and which take users by drag only. A user is dragged from the server-level Users folder into one of the role folders to get that role in that project; a user is in one role folder of a project at most, and is dragged between them to change role or out to lose access.
- What a role allows in its project: an **Owner** does what the owner does today (resolves threads, sets states, edits, creates, renames, moves, trashes, exports) and manages the project's Users folder; a **Member** writes and takes part (edits, creates, comments, replies) but does not resolve, manage users or delete the project; a **Watcher** reads only. Owners and Members press the run buttons; a Watcher has none.
- A project is shown to those with a role in it. The Admin may put themselves in a role folder like anyone; their rights in a project come from that.
- Clerk's organization roles grant nothing by themselves: an organization admin is a user like any other until dragged into a role folder (the subplan Clerk says how the organization's members reach the registry).


## LLM runs and agent sessions

- **A run is the presser's.** The run record carries the person and the connection; what the run posts (threads, replies, revisions, applies) is recorded as the person, with the connection as Via, shown in the thread as the person's name followed by the connection's. The server gives the one-shot a token of its own making for the run, scoped to that person and that project, dropped when the run ends; the connection has no participant and no token of its own any more.
- **Tokens.** A person mints a token from their user page (Create token, with a name; Revoke), good until revoked; the page shows it once. A request carrying it is that person via that name, in every project the person has a role in. An agent session (Claude Code or similar) is given one by the person in its prompt; its turn and build loops are unchanged otherwise.
- **The owner's tokens on a Local server.** The owner has a user page too, under the server's settings, with the same Create token and Revoke, so a thread can say owner via Claude Code instead of plain owner. /instructions serves no token; on a Local server a request without one is the owner as today, so an agent session on the same machine keeps working without ceremony.
- **The desktop.** A saved server holds a token the person minted on it, in place of the connection screen's sign-in; the desktop's own local server needs none.


## Administrator

- A Public server with Clerk has one Admin, named by email in the Clerk section of the settings. Only the Admin writes the server's settings and the LLM connections, and sees every user's page.
- A Local or trusted-network server has no Admin: the owner is the Admin, as today.


## Migration

- At the first start after this plan: the Participants section leaves consensus.json and the Settings popup. The owner participant becomes the server's owner. The llm and member participants are dropped (an agent session gets in with a person's token; members come through Clerk). The LLM connections lose their Token and their participant; their Name and Display stay for the Via.
- Threads and revisions already recorded under the old participant names (user, llm, the connections) keep them as they are; nothing is rewritten.
- `~deploy/cube4.json` and the agent session's instructions change with it (the memory of this is the agent's).


## Out of scope

- Sign-in, sign-up, password reset, invitations and multi-factor: Clerk's, in the subplan.
- An audit log beyond the user's activity history, which is read from what threads and revisions already record.
- Project-level sharing between servers.


## Steps

1. **Scope and trust.** The Clerk section in the settings and the trusted-network wording; the Participants section and the connection tokens leave consensus.json; the migration. Every current behaviour kept on Local and on cube4.
2. **Runs as the presser.** The run-scoped token, the person and Via on the run record and on what the run posts, the thread header showing both. Owners and Members press; Watchers do not.
3. **Users and roles.** Users.json, the role folders in each project, the Users folder and the user pages with Create token and Revoke; the API checks every route against the role; the owner's own user page on Local.
4. **Sign-in.** The subplan Clerk, Steps 2 to 5.
5. **Guide and smoke.** The guide's pages on sharing a server and on roles; the agent instructions page; the smoke covering a Member and a Watcher.
