# User Management

People besides the owner working on the same server, each as themselves: registered by the Admin, signed in once, allowed per project what their role there allows. The owner's design (2026-10-02) is the statements below; the open points are threads. Nothing is decided until its thread is.


## Today

- The participants live in consensus.json, edited in the Settings popup: each has a Name (what threads and revisions record), a Display, a Role (owner, llm or member) and an optional Token. Only the owner resolves threads and writes the settings; only the llm applies; everyone else takes part.
- A request is identified by its token (Authorization: Bearer). A request with no token is the owner: security is relaxed, so the browser signs nothing and the desktop connects as the owner. The llm participant's token is served to whoever reads /instructions.
- cube4 listens beyond the machine: anyone who can reach it acts as the owner. This plan replaces the Owner Token the Readme named.


## User Registry

- Each server keeps a registry of its users: each user's login name, display name and credentials. It is stored in `Users.json` in the data folder, beside consensus.json.
- Credentials are plain passwords, stored as plain text for now. The registry may evolve to Clerk (a user registry and authentication service) one day; today it just works.
- The participants of consensus.json become users: at the first start after this plan the registry is made from them (each participant a user with its Name as login, its Display, and a password made up and printed at that start for the Admin to hand out or change); the llm participant becomes a user too, since an LLM connection posts as a user (below).


## Authentication

- Users are authenticated globally, once: a sign-in (login name and password) on the server, good for every project the user has a role in.
- The browser page has a sign-in box (shown when the API answers 401) and a Sign out; the desktop keeps the sign-in per saved server and signs in when it connects. A request with no sign-in is refused.
- The Project Tree always holds a **Users** folder at the server level, with an item for each user with access to the server. Clicking a user opens a tab page with the user's details, permissions (the projects and the role in each) and a history of activity on the server (the threads, replies, revisions and state changes by that user, read from the data, newest first).


## Authorization

- Authorization is per project. A project has lists of **Owners**, **Members** and **Watchers**, as three role folders inside its own **Users** folder. A user is dragged from the server-level Users folder into one of the role folders to get that role in that project; a user is in one role folder of a project at most, and is dragged between them to change role or out to lose access.
- What a role allows in its project: an **Owner** does what the owner does today (resolves threads, sets states, edits, creates, renames, moves, trashes, exports) and manages the project's Users folder; a **Member** writes and takes part (edits, creates, comments, replies) but does not resolve, manage users or delete the project; a **Watcher** reads only. A project is shown to those with a role in it.
- An LLM connection's configuration offers a user selection from the users in the project's Owners or Members: the connection posts as that user.


## Administrator

- There is one Admin per server. Only the Admin manages the user registry (adds, edits and removes users, sets their passwords) and the server's settings.
- The Admin's own rights in a project come from its role folders like anyone's; the Admin may put themselves in.


## Out of scope

- Hashed passwords, password reset, self-registration, invitations by mail, sessions with expiry: a later plan, or Clerk.
- An audit log beyond the user's activity history, which is read from what threads and revisions already record.
