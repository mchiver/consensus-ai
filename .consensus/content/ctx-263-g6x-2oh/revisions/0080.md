# Consensus

## Purpose

A web app where a person (the owner) and an LLM work a plan through, thread by thread, from its Draft until every thread is resolved and applied. Plain files. Since plan Consensus Desktop, Step 1 (2026-10-01), the server calls no LLM and reads no code: every LLM takes part through the API as an llm participant, from wherever it runs (the agent session, on "your turn in Consensus"; since Run Shapes Step 3 the server's own LLM connections too, each a participant of its own, run in a project's folder on the server's machine). The desktop shows several servers at once, each a root of its tree (Run Shapes Step 5). Security is relaxed for now: a request with no token is the owner (accepted on cube4's private network). Plan User Management (under the master plan Teams, 2026-10-18 and 19) replaces that with Clerk sign-in on sold servers, roles per project and runs as the presser; its Step 1 (2026-10-19) added the Clerk settings section and the trusted-network wording; its Step 2 (2026-10-19) made every request the owner account: an agent session names itself with the X-Consensus-Service header, a run carries a token the server mints for it and forgets when it ends, any other token is refused, and what an LLM posts carries the byline "<service> by <owner>" ("Claude-CLI by User"); the participants list and the connection tokens are gone from consensus.json (Owner in their place).

## Conventions (CLAUDE.md)

- Tabs; spaces inside brackets; braces on new lines; no arrow functions; async/await.
- UPPER_CASE constants, lower_case locals and functions, PascalCase parameters and exports; never camelCase. Descriptive names; separator lines between blocks.
- `~` folders stay out of git. Commits carry no attribution trailers.

## Settled decisions

- Threads: contested, then resolved (since Multiuser Step 1, 2026-10-21, by the one who started it or an Owner of the project, a Member for their own threads; the owner alone before: one Resolve button, a typed reply as the outcome, else the last reply's outcome or recommendation accepted, or Comment and resolve), then applied by anyone with write access as a new revision (the LLM alone before; an account acting for a person, a run or an agent session, also serves the resolved threads waiting on that person, applying them as the presser). A reply reopens a resolved thread. An Owner may delete any thread. The page says the same before the server does (`public/js/threads.js`, Multiuser Step 2: the Resolve button to the starter and the Owners, Comment and resolve to Owners and Members, the State picker disabled for anyone but an Owner), and the state line leads with "waiting on you N", the resolved threads one is to apply counted with the contested ones. Who a thread waits on (`Rules.Turn`): contested, its parties, the starter, the Owners, everyone who replied in it and the LLM speakers, minus the last replier, never a person who has not joined in; resolved, the LLM speakers that apply it, never a person (2026-10-22, the owner's word: a thread you resolve is off your list; Step 1 had the starter and the Owners); applied, nobody.
- Plan states (Draft, Plan, Working, Finished; the first was Proposal before UI Tweaks V, renamed once at start where the list still had it) come from settings; an Owner sets them (since Multiuser Step 1; anyone before); they never depend on threads. The tree's "New Draft" is named after the first state.
- Projects hold trees of folders, plans, documents and corpora. Subplans: a plan holds plans only, organizational, no rules between states; a Subplan's prompt carries its parent plans as text (plan Plans and Subplans).
- Every project has a Context folder, first in its tree, holding its Readme (this document) and any other document: documents only, flat, and documents nowhere else; neither the folder nor the Readme is renamed, moved, copied or deleted. The agent session keeps the Readme up to date (an edit through the API); it is read by everyone who works on the project.
- Every LLM takes part through the API as an llm participant: the hand-made `llm` for the agent session (Claude Code replies, applies, drafts plans, keeps the Readme and implements plans when asked), and since Run Shapes Step 3 (2026-10-12) one per LLM connection of the settings, named `<connection>@<server name>`, with a token the server makes and keeps on the connection. A run (since LLM Tasks Step 1 one of the server's tasks, Answer, Work and Session shipped in place of Review, Build and Session; a project enables the ones it uses) is started by any participant but an llm one, works in the project's folder on the server's machine, one per connection and, since Multiuser Step 3 (2026-10-21), one per plan at a time: a press while either has a run on is queued behind it in press order (Status queued, Queued, Behind), told so, and packaged again when its turn comes; its record with who asked in `<config>/runs/`. ## Glossary

- **Plan**: any text item with revisions and threads and a state; a **document** has the revisions only. "Plan" was the old umbrella word (gone with plan Plan Nomenclature, 2026-10-14).
- **Thread**: a comment on a passage (anchored) or the whole document. **Apply**: the LLM puts a resolved thread's outcome into the text.
- **Context folder**: a project's first folder, documents only; **Readme**: this document, the project's background (titled Context before 2026-10-01).
- **Sidecar mode** (named in the docs 2026-10-23): an open LLM session (Claude Code) beside an open Consensus, prompted with "check consensus" or "your turn" instead of the page's task buttons; the more powerful way, since the session has every tool and all the context its harness keeps; one project's at a time, the plans made in Consensus and carried out in the session, the server's other projects left to sessions of their own. Defined in `.definitions/sidecar-mode.md`, the served instructions and the docs' Ways of working page.
