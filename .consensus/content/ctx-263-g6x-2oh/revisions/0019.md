# Consensus

## Purpose

A web app where a person (the owner) and an LLM work a proposal through, thread by thread, until every thread is resolved and applied and the proposal becomes a plan. It listens on the settings' Host (127.0.0.1 by default; --host overrides; security relaxed for now: no token is the owner, accepted on cube4's private network; an Owner Token plan is for later); plain files; the LLM is called only when the owner presses Send to LLM.

## Architecture and where things live

- Node + Express server, AngularJS + Bootstrap page, Monaco for editing. No TypeScript, minimal dependencies (express, angular, bootstrap, marked, monaco-editor, yauzl, ignore).
- `.guides/build-with-consensus.md`: how an agent session works with Consensus, and the build loop; served at `GET /instructions` (`src/Instructions.js`) with a This server section first (the API address from the request's Host, the llm token), so any session is started with "read the instructions at http://<server>:<port>/instructions".
- `bin/context-server.js` + `src/ContextServer.js`: the optional context server; `src/ContextServers.js` is Consensus's side of it.
- `bin/consensus.js`: starts the server. At start `src/Migrate.js` moves a data folder from before Global Ids to global ids once (backup `<folder>-before-ids`, table `ids.json`), then `Prepare()` makes the Default project a new data folder needs.
- `src/Server.js` start-up, settings defaults, indexing; `src/Api.js` every REST route and rule enforcement; `src/Rules.js` the consensus rules as pure functions; `src/Store.js` the data folder; `src/Tree.js` project trees; `src/Llm.js` prompts, answer parsing, callers; `src/Index.js` + `src/Vectors.js` search; `src/Corpus.js` + `src/Zip.js` attached zips; `src/Filter.js` which files a corpus lets in; `src/Anchors.js` thread anchors; `src/ProjectPort.js` project export and import; `src/Ids.js` global ids.
- `public/index.html` + `public/js/*.js` (one controller per pane: sidebar, header, read, edit, revisions, threads, waiting, search, corpus; plus tabs, sessions, subplans, ports (the export / import popup) and menus, the one popup menu) + `public/css/consensus.css`.
- Tests: `node --test`; `test/Ui.test.js` drives headless Chrome or Edge.
- Deployment: `Dockerfile` (node:22-alpine, runs as node, data in the `/data` volume, health check on `/api/me`), `.dockerignore`, `compose.yaml`. The live server is on cube4 (`http://cube4:3500`, compose in `~/consensus/`, volume `consensus-data`, TZ America/New_York); no registry: built on the dev machine and sent with `docker save | ssh claude@cube4 docker load`. The port is published on IPv4 only, since cube4 also resolves to global IPv6 addresses and Chrome's Private Network Access then blocked the page's files. The agent session works there over the API with cube4's own llm token. SIGTERM (docker stop) closes the server cleanly.

## Data (~data, never in git)

- `projects.json`: project names and display order. `projects/<id>/project.json`: the tree and the project's Context id.
- `proposals/<id>/`: proposal.json, proposal.md, threads.json, revisions/, index.json. Kinds: plan (threads, state), document (no threads, no state), context (one per project).
- `projects/<project>/corpora/<id>/`: a corpus of the project (corpus.json, and for an attached one its zip and index); it moves and copies with its project. `trash/<id>/`: deleted proposals and corpora.
- Ids are global (`src/Ids.js`): `<kind>-xxx-xxx-xxx`, three-letter kind (`prj pln doc ctx fld cor thr rep rev run`), three groups of three base36 characters from the crypto source; Default is `default`. Revisions carry `Id` and `Parent`, `proposal.json` its `Head`, Applied records a `RevisionId`; the revision number is only the sequence on one server. `ids.json` maps the old ids (letter + 8 hex) to the new, and the API and page still open items by them.

## Conventions (CLAUDE.md)

- Tabs; spaces inside parentheses and brackets; braces on new lines; no arrow functions; async/await.
- UPPER_CASE constants, lower_case locals and functions, PascalCase for parameters and exported names; never camelCase.

## Settled decisions

- Threads: contested, then resolved (owner only), then applied (by the LLM, a new revision tied to the thread). The owner resolves with Reply and resolve (their reply is the outcome), plain Resolve (accepting the outcome or recommendation in the LLM's last reply), or Comment and resolve on a new thread (`Resolve: true` on POST threads; the comment is the outcome). A reply reopens a resolved thread. The owner may delete any thread; its revision keeps "(deleted thread)".
- Plan states come from settings (Proposal, Plan, Working, Finished); anyone sets them; they never depend on threads.
- Corpus files: no list of file types. Include/Exclude (per corpus, edited in its view) and .gitignore files choose them; any file let in is read unless larger than MaxFileKilobytes or binary. The LLM has list_files and read_file (Corpus, or the older Zip).
- Projects hold trees of folders, plans, documents and corpora; one open at a time; everything reorders by drag and drop; copy/paste makes whole copies.
- Subplans: a plan holds plans only (its `Items` in the tree); the tie is organizational, with no rules between states. Subplans fold under their parent and move, copy and go to the trash with it. Started from a plan's row (+), its heading, a new thread or reply, or selected text (`public/js/subplans.js`); from a thread, the thread gets a reply linking to the Subplan. A Subplan's prompt carries the plans above it as text without threads (the Parent plans part); a parent's prompt lists its Subplans by title.
- The LLM has no tools: one prompt in, one JSON answer out (reply, apply, context actions), carried out through the API's rules. Search and prompts stay within the plan's project.
- Every project has a context (Default too), always in the prompt, rewritten by the LLM directly as revisions; stale changes are refused; people edit it freely. Initialize context is a button, never automatic.
- Two kinds of LLM, both the one `llm` participant: the one-shot LLM (Send to LLM, for example Ollama) reviews, replies, applies and keeps the context, and never builds; the agent session (Claude Code) initializes contexts and implements plans. Each task goes to the model that suits it.
- Build loop: a plan with every thread applied is built on the owner's word; the agent sets it Working, implements only what it says, runs the tests, and posts a contested build log thread naming its model. Resolving it accepts: the agent applies it, commits (titled after the plan, no trailers), sets Finished, and updates this context. A reply sends it back. A plan with open threads is reported in the chat only.
- Tree rows: each row's actions are in one menu (⋯ on hover and on the current row, or a right-click); Delete is there only, confirmed on the row (no Delete in the heading or the corpus view). The open project carries a solid green dot, the others a hollow circle.
- Tabs: every item, Waiting and Search open as tabs (one per item, kept in sessionStorage), each keeping its view, threads filter (a new tab starts at Waiting on me; a selected thread the filter leaves out is deselected) and unsaved edit; a tab's menu (▾ or a right-click) closes it, the others, those to its right or all, and detaches it into its own window (`?detached=1`); a detached tab stays in the strip, ghosted, with Re-attach and Close in its menu; the windows talk over a BroadcastChannel (`public/js/tabs.js`). Ctrl+E switches the open item between Read and Edit.
- LLM sessions: Send to LLM opens the plan's session panel (`public/js/sessions.js`), centered within its content area, moved by its heading and sized by a corner grip (place and size remembered per browser; Reset recenters), one per plan, running concurrently across tabs. It shapes the prompt (context, search, waiting / open / all threads; open is the default) with its size part by part, sends it to a destination (the llm participant's `Destinations`: Ollama, Claude CLI) or Manual copy / paste, and keeps a run log per plan in `runs.json`. An answer may ask for more (`Requests`: list_project, read_plan, read_revision, read_file, search; read-only, within the project); Consensus answers them in the next prompt of the session, up to 5 answers, and Manual copy / paste goes on with Continue.
- Context servers: an optional server beside Consensus (own settings file, `Host` 127.0.0.1 by default, port 3600, a token on every route, read-only, paths confined to each corpus Root) keeps live corpora (Root + Include/Exclude + every nested .gitignore, nothing assumed; indexed with our own index and re-indexed by a file watcher) and passes prompts to local LLMs. Consensus lists them in `ContextServers` in consensus.json; offline ones break nothing. **+ link** adds a server's corpus to a project like a zip; search interleaves its hits with ours by rank; read_file, list_project and Initialize context reach it; each Inference item is a session destination named "<server> / <item>".
- UI: VS Code style tree, hidden or shown from the tab bar, sortable (none, name, created, updated; display only, the project's order is kept; edge drops off while sorted) with optional last-updated stamps; two-line header; threads pane and edit preview toggles, and the Highlight picker (all or open threads), remembered per browser; buttons colored by purpose with inline SVG icons (one symbol set in index.html) and a hover lift; light/dark and small/normal/large.
- Project export and import (`src/ProjectPort.js`, API first so the agent session can carry projects to a remote Consensus with the llm token; the page has Export project on a project's menu and Import beside New project): one json object (`Format: consensus-project`, `Version: 1`) with the tree, context, every proposal with threads and every revision, corpora settings and file lists, and the context servers used; never tokens, indexes, runs or zips. A project not here comes in with ids intact; one here needs Mode `copy` ("Copy of <name> (imported <date>)", every id new) or `merge` (revisions matched by global Id; a conflict gets a merge revision, Parent + Merged, with the newer text; threads gain replies and resolve / apply records; nothing removed). Attached corpora arrive waiting for their zip. JSON body limit 64 MB.

## Glossary

- **Proposal**: any text item with revisions; a **plan** is the kind with threads and a state.
- **Thread**: a comment on a passage (anchored) or on the whole document.
- **Apply**: the LLM puts a resolved thread's outcome into the text.
- **Corpus**: files offered to a project: **attached** (a zip kept by Consensus) or **linked** (a context server's folder), one record shape with `Source`, `Include` and `Exclude`.
- **Context**: this document.
