# Consensus

## Purpose

A local web app where a person (the owner) and an LLM work a proposal through, thread by thread, until every thread is resolved and applied and the proposal becomes a plan. Localhost only; plain files; the LLM is called only when the owner presses Send to LLM.

## Architecture and where things live

- Node + Express server, AngularJS + Bootstrap page, Monaco for editing. No TypeScript, minimal dependencies (express, angular, bootstrap, marked, monaco-editor, yauzl).
- `.guides/build-with-consensus.md`: how an agent session works with Consensus, and the build loop.
- `bin/consensus.js`: starts the server; `migrate-ids` converts an older data folder's ids once.
- `src/Server.js` start-up, settings defaults, indexing; `src/Api.js` every REST route and rule enforcement; `src/Rules.js` the consensus rules as pure functions; `src/Store.js` the data folder; `src/Tree.js` project trees; `src/Llm.js` prompts, answer parsing, callers; `src/Index.js` + `src/Vectors.js` search; `src/Corpus.js` + `src/Zip.js` uploaded zips; `src/Anchors.js` thread anchors; `src/Ids.js` the id migration.
- `public/index.html` + `public/js/*.js` (one controller per pane: sidebar, header, read, edit, revisions, threads, waiting, search, corpus) + `public/css/consensus.css`.
- Tests: `node --test`; `test/Ui.test.js` drives headless Chrome or Edge.

## Data (~data, never in git)

- `projects.json`: project names and display order. `projects/<id>/project.json`: the tree and the project's Context id.
- `proposals/<id>/`: proposal.json, proposal.md, threads.json, revisions/, index.json. Kinds: plan (threads, state), document (no threads, no state), context (one per project).
- `corpora/<id>/`: an uploaded zip, its file list and index. `trash/<id>/`: deleted proposals and corpora.
- Ids: kind letter + 8 hex (`p` proposal, `z` zip, `j` project; Default is `default`); folders `f…`, threads `t…`, replies `r…`.

## Conventions (CLAUDE.md)

- Tabs; spaces inside parentheses and brackets; braces on new lines; no arrow functions; async/await.
- UPPER_CASE constants, lower_case locals and functions, PascalCase for parameters and exported names; never camelCase.
- Descriptive names; separator comment lines between blocks; comments say why.
- Folders starting with `~` stay out of git. Commits carry no attribution trailers.

## Settled decisions

- Threads: contested, then resolved (owner only), then applied (by the LLM, a new revision tied to the thread). The owner resolves with Reply and resolve (their reply is the outcome) or plain Resolve (accepting the outcome or recommendation in the LLM's last reply). A reply reopens a resolved thread. The owner may delete any thread; its revision keeps "(deleted thread)".
- Plan states come from settings (Proposal, Plan, Working, Finished); anyone sets them; they never depend on threads.
- Projects hold trees of folders, plans, documents and zips; one open at a time; everything reorders by drag and drop; copy/paste makes whole copies.
- The LLM has no tools: one prompt in, one JSON answer out (reply, apply, context actions), carried out through the API's rules. Search and prompts stay within the plan's project.
- Every project has a context (Default too), always in the prompt, rewritten by the LLM directly as revisions; stale changes are refused; people edit it freely. Initialize context is a button, never automatic.
- Two kinds of LLM, both the one `llm` participant: the one-shot LLM (Send to LLM, for example Ollama) reviews, replies, applies and keeps the context, and never builds; the agent session (Claude Code) initializes contexts and implements plans. Each task goes to the model that suits it.
- Build loop: a plan with every thread applied is built on the owner's word; the agent sets it Working, implements only what it says, runs the tests, and posts a contested build log thread naming its model. Resolving it accepts: the agent applies it, commits (titled after the plan, no trailers), sets Finished, and updates this context. A reply sends it back. A plan with open threads is reported in the chat only.
- Tabs: every item, Waiting and Search open as tabs (one per item, kept in sessionStorage), each keeping its view and unsaved edit; a tab detaches into its own window (`?detached=1`) and re-attaches over a BroadcastChannel (`public/js/tabs.js`).
- LLM sessions: Send to LLM opens the plan's session panel (`public/js/sessions.js`), within its content area, one per plan, running concurrently across tabs. It shapes the prompt (context, search, waiting / open / all threads; open is the default) with its size part by part, sends it to a destination (the llm participant's `Destinations`: Ollama, Claude CLI) or Manual copy / paste, and keeps a run log per plan in `runs.json`. An answer may ask for more (`Requests`: list_project, read_plan, read_revision, read_file, search; read-only, within the project); Consensus answers them in the next prompt of the session, up to 5 answers, and Manual copy / paste goes on with Continue.
- UI: VS Code style tree; two-line header; threads pane and edit preview toggles remembered per browser; light/dark and small/normal/large.

## Glossary

- **Proposal**: any text item with revisions; a **plan** is the kind with threads and a state.
- **Thread**: a comment on a passage (anchored) or on the whole document.
- **Apply**: the LLM puts a resolved thread's outcome into the text.
- **Corpus**: an uploaded zip whose text files are indexed with the project.
- **Context**: this document.
