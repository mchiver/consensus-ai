# Consensus

## Purpose

A web app where a person (the owner) and an LLM work a proposal through, thread by thread, until every thread is resolved and applied and the proposal becomes a plan. Plain files; the LLM is called only when the owner asks. Security is relaxed for now: a request with no token is the owner (accepted on cube4's private network; an Owner Token plan is for later).

## Architecture and where things live

- Node + Express, AngularJS + Bootstrap, Monaco. No TypeScript; few dependencies (express, angular, bootstrap, marked, monaco-editor, yauzl, ignore).
- `bin/consensus.js` starts it; `src/Server.js` start-up and indexing; `src/Api.js` every route and rule; `src/Rules.js` the consensus rules; `src/Store.js` the data folder; `src/Tree.js` trees; `src/Llm.js` prompts and callers; `src/Index.js` + `src/Vectors.js` search; `src/Corpus.js`, `src/Zip.js`, `src/Filter.js` corpora; `src/Anchors.js` anchors; `src/ProjectPort.js` export and import; `src/Ids.js` ids.
- Workers (plans Workers, Review, Build): `src/Workers.js` Consensus's side (tokens, hello, the job queue); `bin/worker.js` + `src/Worker.js` the worker (`worker.json`, jobs, Commit/Push, `--mcp`, `--bash-guard`); `src/Workspace.js` its glob/grep/read; `src/Mcp.js` the plan tools for claude; `public/worker/` its page; `public/js/build.js` the Build dialog. The worker app (plan Worker Electron App): `worker-app/` (main.js, preload.js, Settings.js, Manager.js, page/), `npm run app`, Electron a devDependency, run from the checkout.
- `public/index.html`, `public/js/*.js` (one file per pane or feature), `public/css/consensus.css`.
- `.guides/build-with-consensus.md`: how an agent session works here; served at `GET /instructions` with the server's address and llm token first.
- Tests: `node --test`; `test/Ui.test.js` and `test/WorkerUi.test.js` drive headless Chrome or Edge.
- Deployment (plan Docker Image): `Dockerfile`, `.dockerignore`, `compose.yaml`. The live server is cube4, `http://cube4:3500` (compose in `~/consensus/`, volume `consensus-data`); no registry: built on the dev machine, sent by `docker save | ssh claude@cube4 docker load`. Port published on IPv4 only (Chrome's Private Network Access blocked the page over cube4's global IPv6). The agent session works there over the API with cube4's llm token.

## Data (the data folder, never in git)

- `projects.json` (names, order); `projects/<id>/project.json` (tree, Context id, Workspace { Worker, Name }); `projects/<id>/corpora/<id>/`; `proposals/<id>/` (proposal.json, proposal.md, threads.json, revisions/, index.json, runs.json); `trash/`.
- Proposal kinds: plan (threads, state), document (neither), context (one per project).
- Ids (plan Global Ids): `<kind>-xxx-xxx-xxx`, kinds `prj pln doc ctx fld cor thr rep rev run job`, base36 from the crypto source; Default is `default`. Revisions have `Id` and `Parent`, proposals a `Head`, Applied records a `RevisionId`; a revision number is only the sequence on one server.

## Conventions (CLAUDE.md)

- Tabs; spaces inside brackets; braces on new lines; no arrow functions; async/await.
- UPPER_CASE constants, lower_case locals and functions, PascalCase parameters and exports; never camelCase. Descriptive names; separator lines between blocks.
- `~` folders stay out of git. Commits carry no attribution trailers.

## Settled decisions

- Threads: contested, then resolved (owner only: Reply and resolve, Resolve accepting the LLM's last outcome or recommendation, or Comment and resolve), then applied by the LLM as a new revision. A reply reopens a resolved thread. The owner may delete any thread.
- Plan states (Proposal, Plan, Working, Finished) come from settings; anyone sets them; they never depend on threads.
- Projects hold trees of folders, plans, documents and corpora. Subplans: a plan holds plans only, organizational, no rules between states; a Subplan's prompt carries its parent plans as text (plan Plans and Subplans).
- Every project has a context (this document), in every prompt, rewritten by the LLM as revisions and edited freely by people; kept under `Context.MaxCharacters` (12,000) by compacting. Initialize context is a button, never automatic.
- One prompt, one JSON answer, carried out through the API's rules: reply, apply, context, thread (a new thread on the reviewed plan) and plan (a new plan or Subplan). A call from Consensus has no tools but may ask for more (`Requests`, up to 5 answers); a worker's review has read-only tools instead (glob, grep, read, and the plan tools).
- All LLMs are the `llm` participant. **Review** (on a plan, or on one thread, which alone is sent and acted on) replies, applies, opens threads and plans, keeps the context, never builds; Consensus calls it, or a worker runs it. **Build** (the page's button) has a worker implement a plan. The agent session (Claude Code) initializes contexts and implements plans when asked.
- Build loop (agent session): a plan with every thread applied is built on the owner's word; the agent sets it Working, implements only what it says, tests, and posts a contested build log naming its model. Resolving accepts: apply it, commit (titled after the plan), set Finished, update this context. A reply sends it back.
- Build (worker, plan Build): enabled when the project's workspace has Build settings on an online worker and every thread is applied; sets Working; claude -p in the workspace as it is, Bash held to Build.Commands by a hook. The build log is the receipt: resolving it applies it, writes the build's context and sets Finished; a reply sends it back (Build again, the new log a reply on the same thread).
- No automated git: workers and builds never branch, commit or push on their own; git is the owner's, outside Consensus or with Commit and Push on the worker's page. A git workflow is a later plan.
- Corpora are attached zips; Include/Exclude and .gitignore choose the files, no list of types. Linked corpora and context servers were retired by plan Workers.
- Workers (plan Workers): run beside the code and connect out to Consensus (`Workers` in consensus.json, each its own token); hello, a job ask held open 30 s, offline after 60 s; one job at a time. A project names one workspace (a folder a worker offers); a worker's Inference items are destinations "<worker> / <item>". The worker's page (127.0.0.1:3700) shows the job, its tool calls and answer, and the last 50 jobs.
- Worker app (plan Worker Electron App): one Electron window runs workers in its own process, one workspace per worker, every worker carrying all the app's LLMs; app.json in `%APPDATA%/consensus-worker`; each worker's worker.json and jobs.json under `<user data>/workers/<Name>/` so it also runs from a shell; a tab per worker shows the worker's own page from its free port in a WebContentsView; tokens are still added to the server's consensus.json by hand; closing the window stops every worker; no tray, no packaging.
- Export and import (plan Project Import and Export): a whole project as one json object, API first (owner or llm token), never tokens, indexes, runs or zips. A project not here comes in with ids intact; one here is imported as a copy ("Copy of <name> (imported <date>)", every id new) or merged (revisions by Id; a conflict gets a merge revision with the newer text; nothing removed).
- UI (plans UI Tweaks, II, III, Tabs): VS Code style tree with one actions menu per row; tabs per item, detachable into windows; light/dark and small/normal/large.

## Glossary

- **Proposal**: any text item with revisions; a **plan** is the kind with threads and a state.
- **Thread**: a comment on a passage (anchored) or the whole document. **Apply**: the LLM puts a resolved thread's outcome into the text.
- **Corpus**: files offered to a project, attached or linked.
- **Context**: this document.
