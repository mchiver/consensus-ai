# Project Context

Each project carries a running context: a short, curated account of what the project is and what has been decided, kept up to date by the LLM and the people working in it. Every LLM call includes it, and the LLM may change it.

This comes before the tabs work (the "Later: tabs" section of Consensus UI Tweaks).

## Why

Today a call gets the proposal, its threads, and up to 10 search hits per waiting thread from the project's plans, documents and uploaded files.

- **Fragments only.** Search returns passages that match a thread's words, never an overview of the project: its purpose, architecture, conventions, or settled decisions.
- **No memory between calls.** Each call starts cold; what a finished plan settled comes back only if search happens to find it.
- **Nothing is distilled.** Finished plans pile up as raw text.

A context that is always in the prompt gives every call the same orientation, and the LLM records what each plan changes so the next call starts from it.

## What it is

- One context per project, a new item kind: `context`. It is markdown with revisions, edited in Monaco like a document, with no threads and no state.
- It is pinned at the top of its project's tree and cannot be moved, copied or deleted.
- It holds the project's purpose, architecture and where things live, conventions, settled decisions, a glossary, and open questions. It points to files and plans (for example "see `src/Store.js`") rather than copying them.

## How the LLM uses it

- Every call includes the project's context, right after the rules and before the proposal.
- The answer may carry a new action, `context`: the whole new text and a reason. It becomes a new revision of the context, made from the revision the call was given; a stale one is refused, as a stale apply is.
- When a project has no context yet, the call asks the LLM to write one from what it has: the proposal, the search hits, and the project's file list.
- The LLM keeps it within a size limit by rewriting and compacting, not only appending.
- Any change the LLM makes is named in its reply on the thread it was working on, so it never changes silently.

## Starting a project from a codebase

- Create the project, upload the codebase as a zip, then use **Initialize context** on the project.
- That call gives the LLM the zip's file list and its key files (readme, package manifest, entry points) and asks it to write the first context.

## Settings

- `Context.MaxCharacters` in `consensus.json`: the size the context is kept under; 12,000 characters (about 3,000 tokens) by default.

## What stays as it is

- **Plans** remain the unit of discussion and approval.
- **Documents** remain for longer reference material people write; small "notes for the LLM" documents can move into the context.
- **Zips** remain the raw codebase, and **search** still grounds the details. The context is the map; documents and zips are the territory.
