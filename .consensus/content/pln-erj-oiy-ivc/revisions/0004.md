# MCP Server

Consensus has one door, the REST API, and every LLM comes through it: an agent session with curl in sidecar mode, a run from the page with its packaged prompt, a local model through the server's tool loop. Codex, Cursor, Claude Desktop and the other MCP clients do not speak curl; they speak the Model Context Protocol, JSON-RPC 2.0 over stdio or over HTTP. This plan gives Consensus an MCP server over the whole of its API, in both transports, written in the repository without a library. It reconstitutes the `src/Mcp.js` that the Workers build had and Consensus Desktop Step 1 removed, now over the API instead of a worker's job.

Three statements it rests on:

1. **One interface, implemented once.** Every operation of Consensus is defined once, with its name, what it does, its parameters and who may call it, and performed by one function. The REST API, the MCP server and the run's tools are three faces of that one definition; none has an operation of its own, and nothing reads or writes the store on its own. The rules, the roles, the revisions and the events are the operations', so an MCP client gets exactly what a curl session gets, no more and no less. *Decided 2026-10-23 (the tool set thread, resolved with a reply: include all of them, a single interface definition implemented the same everywhere).*
2. **No library.** MCP is small where we use it: `initialize`, `notifications/initialized`, `ping`, `tools/list` and `tools/call`, one JSON object per message. The old module did it in 160 lines; this one is written the same way, with a test that pins the protocol.
3. **The words are the same.** "Check consensus", "your turn" and "build it" mean what the instructions say whatever the transport; sidecar mode's one-project rule holds; the byline reads `<service> by <person>` as for any session.


## The interface definition

`src/Operations.js` holds the definition and the implementation of every operation the API has today, the sixty-four routes of `src/Api.js`: for each, its **name** (`read_plan`, `reply`, `apply`, `set_state`, `create_project`, `export_project`, `mint_token` and so on), a **description** a model can read, its **parameters** with their types and which are required, the **action** `src/Roles.js` checks it against, and the **function** that performs it: `Operation( Participant, Arguments )`, resolving the JSON the route answers today, or throwing a refusal with the status and the sentence the route answers today. The functions are the route bodies as they are now, moved out of `Api.js` one by one with their helpers, the store's queue and the events kept inside them, so that nothing changes in what the server does.

`src/Api.js` keeps the routing only: each route is its HTTP method and path mapped to an operation, the path parameters, the query and the body folded into one `Arguments` object, the result sent as JSON. The middleware (identify, authorize, the Clerk routes, the import's body limit) stays where it is. The API's behaviour and its tests do not change; `test/Api.test.js` is the net under the move.

## The MCP module

`src/Mcp.js` holds the protocol, with no transport in it:

- `Handle( Message, Participant )`: one JSON-RPC message in, the reply out (or nothing for a notification). `initialize` answers the protocol version (`2025-06-18`, or the client's when it is one we know), the server's name and version, and `capabilities: { tools: {} }`; `ping` answers `{}`; `tools/list` the definition in MCP's form (`name`, `description`, `inputSchema`), every operation a tool; `tools/call` runs the operation as the participant and answers `content: [ { type: "text", text } ]`, with `isError: true` and the refusal's sentence when the operation refused. An unknown method is `-32601`, bad JSON `-32700`, a bad argument `-32602`. A batch (an array) is answered as an array.
- `Project` is a project's id or its name wherever an operation takes one; the tools that take a plan take its id.

## Who the caller is

The same as for any request. The stdio relay says who it is with `--service <name>` (the `X-Consensus-Service` header; `MCP` when none is given, so the byline reads "MCP by User") or `--token <token>` for an account's token on a shared server; the HTTP transport reads the request's own headers, as the API does. On a Local server a relay with neither is the owner. Every operation is then checked by its action, so a Watcher's MCP reads and a Member's replies, as their roles say; the plan's State stays an Owner's.

## The stdio transport

`bin/mcp.js`: `node bin/mcp.js --server http://127.0.0.1:3500 [--service <name> | --token <token>] [--project <id or name>]`. It reads newline-delimited JSON-RPC from stdin, answers on stdout, logs to stderr only (stdout is the protocol), and exits when stdin ends. It runs on the client's machine, so it reaches the operations the way a session does, over the server's HTTP transport (below) with the caller's header: one request per message, the answer passed back. `--project` fills `Project` for the tools that take one and leave it out, which is how sidecar mode's one-project rule is set for a client; without it the client names the project, or finds it as the instructions say.

The relay needs a running server, as a session does: when the server does not answer, every call is an error that says so, and the relay does not start one. A client's configuration is one line: for Claude Code `claude mcp add consensus -- node <checkout>/bin/mcp.js --server http://127.0.0.1:3500 --service Claude-CLI`, or the same in `.mcp.json`; Cursor, Codex and Claude Desktop take the same command in their own files.

## The network transport

`POST /api/mcp` on the server, the Streamable HTTP transport in its request-response form: a JSON-RPC request (or a batch) in the body, the response as `application/json`. Nothing is server-initiated, so `GET /api/mcp` answers 405 and no `Mcp-Session-Id` is issued; the server is stateless across calls. The route sits under the API, so identify and authorize cover it (`POST /mcp` allowed to every identified caller in the route table; each operation is checked on its own action), a bare request on a Public server is refused as on every route, and the handler calls the operations in the server's process as the request's participant. A client's configuration is the URL `http://<server>:<port>/api/mcp` with the header it uses.

## The run's tools

The Consensus tools a local model gets (`src/Tools.js`) become the same definition in Ollama's form, held to the task's Writes as today: the reading operations at every level, the writing ones when Writes is not none, the project fixed to the run's. The file tools stay as they are. Nothing a run can do changes; its tool list grows to the operations it may call.

## The instructions and the docs

- The served page (`.guides/build-with-consensus.md`) gains a section, **Through MCP**: the two configurations, the tools as the same operations as the routes, the words the same, the one-project rule the same; the `instructions` operation serves the page, so the section is also what an MCP-only client reads first.
- `docs/guide/api.md` is rendered from the definition where it lists the routes, so the reference and the tools cannot drift; `docs/guide/llm.md`: a bullet under "How you hand the page over" for an MCP client, and a section naming the transports; `docs/guide/features.md`: one line under Working with LLMs; the readme's LLM paragraph; the project's Readme in Consensus.

## Tests

`test/Operations.test.js` for the definition (every route of `Api.js` maps to an operation; every operation has a name, a description, parameters and an action); `test/Api.test.js` unchanged and green through the move; `test/Mcp.test.js`: `Handle` as a participant (initialize, ping, tools/list, a call that answers, a call the operation refuses, a batch, bad JSON, an unknown method); the relay over piped streams against a server started in the test on a temporary config (as `test/Tools.test.js` starts one), a thread posted through it carrying the byline; `POST /api/mcp` on the same server, and a bare request refused on a Public one; `test/Tools.test.js` brought to the definition. `node --test` green.

## Out of scope

Resources and prompts (the page and the Readme are operations for now), server-initiated streams, OAuth on the HTTP transport (an account's token or Clerk's session token in the header is the API's own way), a Claude Code plugin or a marketplace listing (the promotion work).
