# MCP Server

Consensus has one door, the REST API, and every LLM comes through it: an agent session with curl in sidecar mode, a run from the page with its packaged prompt, a local model through the server's tool loop. Codex, Cursor, Claude Desktop and the other MCP clients do not speak curl; they speak the Model Context Protocol, JSON-RPC 2.0 over stdio or over HTTP. This plan gives Consensus an MCP server that is nothing but a mapping of that protocol onto the existing API, in both transports, written in the repository without a library. It reconstitutes the `src/Mcp.js` that the Workers build had and Consensus Desktop Step 1 removed, now over the API instead of a worker's job.

Three statements it rests on:

1. **The API stays the one door.** Every MCP tool call becomes an API request as the caller; nothing reads or writes the store on its own. The rules, the roles, the revisions and the events are the API's, so an MCP client gets exactly what a curl session gets, no more and no less.
2. **No library.** MCP is small where we use it: `initialize`, `notifications/initialized`, `ping`, `tools/list` and `tools/call`, one JSON object per message. The old module did it in 160 lines; this one is written the same way, with a test that pins the protocol.
3. **The words are the same.** "Check consensus", "your turn" and "build it" mean what the instructions say whatever the transport; sidecar mode's one-project rule holds; the byline reads `<service> by <person>` as for any session.


## The module

`src/Mcp.js` holds the protocol and the tools, with no transport in it:

- `Handle( Message, Api )`: one JSON-RPC message in, the reply out (or nothing for a notification). `initialize` answers the protocol version (`2025-06-18`, or the client's when it is one we know), the server's name and version, and `capabilities: { tools: {} }`; `ping` answers `{}`; `tools/list` the table below; `tools/call` runs the tool through `Api` and answers `content: [ { type: "text", text } ]`, with `isError: true` and the API's sentence when the API refused. An unknown method is `-32601`, bad JSON `-32700`, a bad tool argument `-32602`. A batch (an array) is answered as an array.
- `Api( Method, Path, Body )` is the one thing a transport supplies: a function that performs the request as the caller and resolves the JSON, or throws the API's `Error` with its status.
- `Tools`: the table, in MCP's form (`name`, `description`, `inputSchema`).

## The tools

One table, each tool one route, named as the run's tools are named where the two overlap so a model that knows one knows the other. `Project` is a project's id or its name; the tools that take a plan take its id.

| Tool | Arguments | Route |
|---|---|---|
| `instructions` | | `GET /instructions`, the page as text, so a client with MCP alone can read the rules |
| `projects` | | `GET /api/projects`: every project with its id, its Readme's id and its tree |
| `list_project` | Project | the one project's tree from the same route |
| `read_plan` | Id | `GET /api/plans/:id`: the text, the revision, the threads with their status, anchor and replies; a document the same |
| `revisions` | Id, Revision? | `GET /api/plans/:id/revisions`, or one revision's text with Revision |
| `waiting` | Project? | `GET /api/waiting`, kept to the project when one is given |
| `thread` | Plan, Text, Anchor? | `POST /api/plans/:id/threads`: on the passage Anchor (plain words), or the whole document |
| `reply` | Plan, Thread, Text | `POST .../threads/:tid/replies` |
| `resolve` | Plan, Thread, Text? | `POST .../threads/:tid/resolve`: with a reply as the outcome, or without one to accept the last |
| `apply` | Plan, Thread, Outcome, Text?, Anchor? | `POST .../threads/:tid/apply`, the current revision read and supplied |
| `reanchor` | Plan, Thread, Anchor | `POST .../threads/:tid/anchor` |
| `write_text` | Plan, Text | `PUT /api/plans/:id/text`, the current revision read and supplied |
| `set_state` | Plan, State | `PUT /api/plans/:id/state` |
| `create_plan` | Project, Title, Text?, Parent?, Kind? | `POST /api/plans`: a plan, or a document with `Kind: "document"` |

The run's Consensus tools in `src/Tools.js` stay as they are: they are bounded to the project a run is on and to the task's Writes, and spoken in Ollama's form. The MCP table is the person's whole API surface for plans and threads, so it is its own, in `Mcp.js`; the names match where the two overlap. Users, settings, runs, import and export are not tools: a client that wants them has the REST API.

## Who the caller is

The same as for any request. The stdio relay says who it is with `--service <name>` (the `X-Consensus-Service` header; `MCP` when none is given, so the byline reads "MCP by User") or `--token <token>` for an account's token on a shared server; the HTTP transport reads the request's own headers, as the API does. On a Local server a relay with neither is the owner. Every tool call is then checked by `authorize` on its own route, so a Watcher's MCP reads and a Member's replies, as their roles say; the plan's State stays an Owner's.

## The stdio transport

`bin/mcp.js`: `node bin/mcp.js --server http://127.0.0.1:3500 [--service <name> | --token <token>] [--project <id or name>]`. It reads newline-delimited JSON-RPC from stdin, answers on stdout, logs to stderr only (stdout is the protocol), and exits when stdin ends. Its `Api` is a fetch to the server with the caller's header. `--project` fills `Project` for the tools that take one and leave it out, which is how sidecar mode's one-project rule is set for a client; without it the client names the project, or finds it as the instructions say.

The relay needs a running server, as a session does: when the server does not answer, every call is an error that says so, and the relay does not start one. A client's configuration is one line: for Claude Code `claude mcp add consensus -- node <checkout>/bin/mcp.js --server http://127.0.0.1:3500 --service Claude-CLI`, or the same in `.mcp.json`; Cursor, Codex and Claude Desktop take the same command in their own files.

## The network transport

`POST /api/mcp` on the server, the Streamable HTTP transport in its request-response form: a JSON-RPC request (or a batch) in the body, the response as `application/json`. Nothing is server-initiated, so `GET /api/mcp` answers 405 and no `Mcp-Session-Id` is issued; the server is stateless across calls. The route sits under the API, so identify and authorize cover it (`POST /mcp` allowed to every identified caller in the route table; the tool calls are checked on their own routes), a bare request on a Public server is refused as on every route, and the handler's `Api` performs the tool's request against the same server over the loopback with the caller's `Authorization` and `X-Consensus-Service` headers copied. A client's configuration is the URL `http://<server>:<port>/api/mcp` with the header it uses.

## The instructions and the docs

- The served page (`.guides/build-with-consensus.md`) gains a section, **Through MCP**: the two configurations, the tools as the same routes, the words the same, the one-project rule the same; the `instructions` tool serves the page, so the section is also what an MCP-only client reads first.
- `docs/guide/llm.md`: a bullet under "How you hand the page over" for an MCP client, and a section naming the transports and the tools; `docs/guide/api.md`: an MCP section with the table above; `docs/guide/features.md`: one line under Working with LLMs; the readme's LLM paragraph; the project's Readme in Consensus.

## Tests

`test/Mcp.test.js`: `Handle` with a fake `Api` (initialize, ping, tools/list, a call that answers, a call the API refuses, a batch, bad JSON, an unknown method); the relay over piped streams against a server started in the test on a temporary config (as `test/Tools.test.js` starts one), a thread posted through it carrying the byline; `POST /api/mcp` on the same server, and a bare request refused on a Public one. `node --test` green.

## Out of scope

Resources and prompts (the page and the Readme are tools for now), server-initiated streams, OAuth on the HTTP transport (an account's token or Clerk's session token in the header is the API's own way), a Claude Code plugin or a marketplace listing (the promotion work), and any change to the run's tools.

## Steps

One build in three checkpoints, each a "done so far / next" note in the chat:

1. **The module and the stdio relay.** `src/Mcp.js`, `bin/mcp.js`, the `bin` entry in `package.json`, `test/Mcp.test.js` for the handler and the relay.
2. **The network transport.** `POST /api/mcp` in `src/Api.js`, the route in `src/Roles.js`, its tests.
3. **The instructions and the docs.** The section on the served page, the guide pages, the features line, the readme and the project's Readme; `node bin/docs.js build`.
