# Consensus Project Features

Consensus has no context for work on an existing codebase: each proposal stands alone.

We need to define a Project mechanism that collects proposals, plans, and context for a single project.

- A **Default** project, created at first start and never deleted, holds ad-hoc items and the existing proposals.
- Every item belongs to exactly one project. To reuse an item elsewhere, copy it and move the copy.
- Storage: `projects/<id>/project.json` holds the project's tree, with items pointing to documents by id. `proposals/<id>/` stays as it is.
- The sidebar should now display a Project tree that lists projects and all of the items in a project.
- Project items are:
    - Plans, what we edit in Consensus. Plans can be one of the following states:
        - Proposal: Open for discussion.
        - Plan: Agreed and ready to build.
        - Working: Being built.
        - Finished: Built and kept as history.
    - The states are a list of strings in `consensus.json`: `"States": [ "Proposal", "Plan", "Working", "Finished" ]`. Anyone can change a Plan's state at any time from a picker in the proposal heading, which replaces the Approve button. No locking for now.
    - Documents: markdown edited in Monaco, with revisions kept, but no threads and no state. The LLM reads them as context but doesn't edit them.
    - Corpus items, any number per project: each is an uploaded zip whose text files are indexed on upload (binary and oversized files skipped). Uploading a new zip over one re-indexes it. The server never reads outside `~data`.
    - Folders to organize any combination of other items. Drag-drop moves an item. Copy-paste copies it whole (text, threads and revisions) under a new id. Copying a folder copies everything in it.
- All Project items are available to the LLM as context. Each Send is one call, with the best passages from our own index (BM25, plus Ollama vectors when configured), searched within the project. The sidebar search box searches the open project too. Giving the LLM tools is a later step.
- Only a single Project should be open/expanded at a time. When tree root is expanded, then the other collapse.

### States

| State | Means | Threads and edits | In search and LLM context |
|---|---|---|---|
| Proposal | Under discussion | Open | Yes |
| Plan | Agreed, ready to build | Open (no locking yet) | Yes |
| Working | Being built | Open | Yes |
| Finished | Built; kept as history | Open | Yes |
| *(Document)* | Reference text, no state | Edits only, no threads | Yes |
| *(Corpus)* | Uploaded zip | None | Yes |

Threads are **Contested**, **Resolved** (waiting to be applied) or **Applied**. A reply to a Resolved or Applied thread makes it Contested again, marked reopened. The rules are unchanged; only the names are new (today's "consensus" becomes Resolved or Applied). A Plan's state doesn't depend on its threads.
