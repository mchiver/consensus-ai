# Accounts and Roles

Who the parties are on a server: the accounts a server knows, and the roles a project gives them. Formalized on 2026-10-19 from the owner's notes, taking over the Authorization section of User Management as the division thread there decided. How a person is identified is User Management's (Clerk identifies, Consensus authorizes); what the rules are among many parties is Multiuser's; what the LLM tasks are is LLM Tasks'. Its six decisions were taken the same day (the decisions thread, resolved with no reply): Service is an account that is not a person, with a role folder of its own; the Administrator holds a role folder like anyone plus the right to assign roles; Members resolve the threads they started; a Service account is a principal beside a person; the Administrator creates and deletes projects.


## Accounts

- **The registry** ties an email address to a user of the server: the Clerk user id, the login name, the display name, the account type and the user's tokens (User Management, Users). It holds no credentials. A Local or trusted-network server has no registry: the owner is everyone.
- **Administrator**: one per server, named by email in the Clerk section of the settings. Full access to the server: manages the accounts (sees every user's page, removes a user, revokes any token), manages the LLM tasks and connections (defines them for the server), creates and deletes projects, and assigns project roles in any project. The Administrator's rights inside a project otherwise come from a role folder like anyone's.
- **User**: everyone else in the registry. A user sees the Users folder, and reaches a project when a role folder of that project holds them, with what that role allows. A user with no role anywhere sees the Users folder alone. Every user mints tokens of their own from their user page, any number, each named, and gives them to whatever acts for them: an agent session beside their editor, a desktop window, a script, a service they run. Whatever runs on such a token runs as that user, in every project the user has a role in, and every record names the user, the token and, when declared, the service: the log shows all three ("Andre · token laptop-agent · Claude Code"), the threads and revisions the byline "Claude Code by Andre"; the token is revoked on the same page (User Management, Tokens).
- **Service**: an account that is not a person and nobody's in particular: a system the team shares, a bot, a scheduled job. It is made by the Administrator on the Users folder, holds tokens the Administrator mints for it, and is placed in role folders like a user. A system that is one user's runs on that user's token instead, and needs no Service account. It presses no LLM task, so no run is ever started or paid for under it. Its activity is recorded under its name like anyone's.


## Project roles

- **A role is what a user may see and do in one project.** Roles are defined per server, the same four in every project, and applied per project through the project's **Users** folder, a fixed folder after the Context folder holding exactly **Owners**, **Members**, **Service** and **Watchers**, none of which is renamed, moved or deleted, and which take accounts by drag only. An account is dragged from the server-level Users folder into one of them to get that role, is in one of them at most, and is dragged between them to change role or out to lose access. Owners and the Administrator do the dragging.
- **Owner**: full access to the project. Resolves any thread, sets the plan States, edits, creates, renames, moves, trashes, exports, manages the project's Users folder, and enables the server's LLM tasks for the project. Projects themselves are created and deleted by the Administrator, who drags in the first Owner.
- **Member**: reads and writes the project. Edits, creates, comments, replies, resolves and applies the threads they started (Multiuser), presses the tasks the writes rule allows. Does not set States, manage users or delete the project.
- **Service**: reads and writes the project through the API as a Member does, presses no task.
- **Watcher**: reads the project and its threads. Presses the read-only tasks, Explain among them, and nothing that writes.
- **Which tasks a role may press is read from the task's Writes level** (LLM Tasks): Writes none is every role's, Watchers included; Writes consensus or files is Owners' and Members'; Service presses none whatever the level. What that comes to today: Owners and Members have Answer, Enhance, Work, Explain and Session; Watchers have Explain; Service has none. A task made later is governed by its record on the day it is made, without a change here.
- **Tasks are defined per server and enabled per project.** The Administrator defines them; an Owner enables, for the project, the ones it has use for.
- **What a project shows.** A project is shown to those with a role in it; the server-level Users folder (names and display names) to every signed-in account; a user's own page to that user and to the Administrator.
