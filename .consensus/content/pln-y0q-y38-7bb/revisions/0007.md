# Documentation

Consensus is an LLM harness: the owner and an LLM work a proposal through, thread by thread, until every thread is resolved and applied, and the plan is built. This plan is the website that tells people that in plain words, shows it, and teaches them to use it.

## The site

One static site in `docs/` at the repository's root, published as it is to the S3 bucket `consensus-ai.liquicode.com` and served at `http://consensus-ai.liquicode.com`. No site generator and no new dependency: the landing page is hand-written HTML, the guide pages are markdown rendered with `marked` by a small build script, and the styling is Bootstrap with the site's own stylesheet.

	docs/index.html            the landing page
	docs/404.html              the not-found page
	docs/guide/pages.json      the guide's pages in order: file and title
	docs/guide/*.md            the user guide, one page each, in markdown
	docs/guide/*.html          the same pages rendered, committed beside their sources
	docs/template.html         the guide's page frame: header, navigation, footer
	docs/css/site.css          the site's styles; bootstrap.min.css is copied beside it by the build
	docs/js/site.js            the theme toggle and the scroll entrances
	docs/images/               the screenshots and the mark
	bin/docs.js                build | screenshots | publish

`node bin/docs.js build` renders every page of `pages.json` into `template.html`, builds the navigation from the pages' titles, copies Bootstrap from `node_modules`, and checks that every internal link and image resolves. The rendered pages are committed, so the site is published from the checkout as it stands, and the guide reads on GitHub as markdown.

The site follows the system's light or dark theme, with a toggle in the header remembered in the browser, as the application does. Text sizes follow the browser's zoom; the layout works from a phone's width up. The mark is a simple SVG drawn for this plan: a text wordmark "Consensus" beside it; there is no other logo.

## The landing page

A single page that says what Consensus does for you, with the application in view. Its sections, in order:

1. **Hero**: the mark, the name, a one-line promise and a screenshot of a plan with its threads. The promise: "Plans you and your LLM actually agree on." Under it: "Consensus turns a draft into a plan your LLM can build, one settled question at a time." Two buttons: Get started and Read the guide.
2. **The problem**: three short cards. Decisions buried in a chat scroll. An LLM that builds the wrong thing, confidently. No record of what was agreed, or why.
3. **How it works**: three steps with a screenshot each. Write a draft. Settle it thread by thread: select a passage and comment, the LLM replies, you resolve, it applies. Build it: the plan is done when every thread is applied, and the build log is a thread too.
4. **What you get**: one sentence each. Every decision is anchored to the text it changed. The LLM applies only what you resolved. Revisions and applied records are the history, with no change log to keep. Works with Claude Code, with local models through Ollama, and with any LLM that can call an API. Your data is plain files in a folder you own.
5. **Where it runs**: the browser page, the desktop application and Docker, with a screenshot of the desktop.
6. **Get started**: the three ways to run it, a few lines each, with a link into the guide: from the checkout, in Docker, and the desktop.
7. **Footer**: the guide, the API reference, the repository and the license (MIT).

The copy is short: no paragraph over three sentences, and no word the guide has not introduced. "Flashy" means motion with restraint: sections and screenshots enter softly as the page scrolls, and nothing moves on its own. A screenshot opens full size when clicked.

## The user guide

Written for people who use Consensus, not for those who maintain it: what a thing is for and how to do it, from the page as it looks. The Readme stays the maintainers' account and the source of every fact; the guide says those facts for a newcomer, one page each:

1. **Getting started**: install from the checkout, start the server, open the page; Docker; the desktop application and its connect screen, including a local server.
2. **Projects, plans and documents**: the sidebar tree, the Context folder and the Readme, folders, Subplans, drag and drop, copy and paste, the trash.
3. **Threads**: selecting text to comment, Contested, Resolved and Applied, reopening, whose turn it is, Reply and resolve, anchors that follow the text.
4. **Editing and revisions**: Read, Edit and Preview, Ctrl+S and Ctrl+E, the revisions record, tabs and detached windows.
5. **Working with an LLM**: the llm participant and its token, "your turn in Consensus" with an agent session, the build loop; in the desktop, LLM connections, workspaces, Review, Build and Session, local models and their tools.
6. **Settings and themes**: host and port, the states, participants and tokens, the themes and sizes.
7. **Export and import**.
8. **The API**: the routes table from the Readme, with one example per kind of call, and the rules in plain words.

Every page has a screenshot wherever the text says to click something. Each page ends with a link to the next.

## Screenshots

Screenshots are made by a script, never by hand, so they can be remade after every change to the page. `node bin/docs.js screenshots` starts a server on a temporary data folder seeded with a demo project (a plan with contested, resolved and applied threads, a document, a Subplan, a Waiting tab with something waiting), drives a headless Chrome or Edge through `test/support/Cdp.js` as `test/Ui.test.js` does, and writes each picture to `docs/images/` at a fixed window size, in the light and the dark theme. The desktop's pictures (the connect screen, the LLM page, a finished run) are made the same way over the desktop started with its own user-data folder. The list of pictures, each with its view and the steps that reach it, is in `bin/docs.js`; the demo project's content is in `docs/demo/` as an export the script imports.

## Publishing

`node bin/docs.js publish` runs `build`, then `aws s3 sync docs/ s3://consensus-ai.liquicode.com --delete` with the AWS CLI and the machine's default AWS profile. Nothing of AWS enters the repository: no keys, no settings file. The bucket serves the site as a static website, index document `index.html`, error document `404.html`. HTTPS is not part of this plan.

## Tests

`test/Docs.test.js`: the build renders every page of `pages.json` into the template, every internal link and image resolves, and the landing page and each guide page hold the header and the footer. The screenshot script is run when a browser is installed, as the page tests are, into a temporary folder, and the test checks that every listed picture was written.

## Not in this plan

Search in the guide, versioned documentation, HTTPS and a CloudFront distribution, a published npm package or Docker image, analytics and comments on the site.
