# Consensus Desktop

I now see the limitations of what we have made.
Including LLM connectivity in a remote environment was a mistake.
The proper way to introduce LLM interoperability to Consensus is to develop a desktop version of Consensus which can interact with the local environment (LLMs and files).

The three steps below are built in order, each accepted on its own build log before the next begins. Steps 1 and 2 are detailed here; Step 3 is sketched, and gets its own detail (a Subplan) once Step 2 is in use.


## Step 1: Consensus Web Server Rework

Remove all LLM connectivity and Workspaces from the existing Consensus server. The Consensus server Web UI and API will now only support the core Consensus functionality. This includes the Project Tree and its items and excludes LLMs and Workspaces. The Review and Build buttons will also be removed. The indexing and RAG functionality will be removed.

Consensus will now be a simplified yet fully functional app for building Plans through direct editing and the turn based Thread/Reply mechanism currently in place.

The current LLM interoperability is still be accomplished through manual updates to Consensus and then tickling the LLM with a "your turn in Consensus" prompt.

The server's data folder will contain the server's configuration file.

The server settings should be fully editable in a popup modal panel. This includes the global theme and style settings.

A project's `Context` will now be a folder named `Context` containing a `Context` document. New Documents (not Plans) can be created within the `Context` folder while the rest of the Project Tree will contain only Plans.

### What goes away

- **Code:** `src/Llm.js` (callers, prompts, sessions, runs, usage), `src/Workers.js`, `src/Worker.js`, `src/Workspace.js`, `src/Mcp.js`, `bin/worker.js`, the worker's page `public/worker/`, the worker app `worker-app/`, `src/Index.js`, `src/Vectors.js`, and the corpora: `src/Corpus.js`, `src/Zip.js`, `src/Filter.js`. The dependencies `yauzl` and `ignore` go with them, and `electron` until Step 2.
- **Routes:** every `/api/workers/*` and `/api/llm/*` route; on a proposal `session`, `send`, `build`, `answer`, `prompt` and `runs`; `/api/projects/:pid/workspace` and `/api/projects/:pid/context/initialize`; `/api/projects/:pid/corpus` and `/api/corpus/*`; `/api/usage`; `/api/search`. `/api/waiting`, `/api/events`, the project, folder, item, proposal, thread, revision, trash, export and import routes stay as they are.
- **The page:** Review, Build, Initialize context and the Review pane (`sessions.js`, `build.js`), the search box and view, the corpus view and Upload zip, the LLM usage line, the project's Workspace picker and line. Waiting on you stays: it is the turn.
- **Settings:** the llm participant's `Call`, `Workers`, `Corpus`, `Context.MaxCharacters` and `Embedding`. The participants stay, roles and tokens included: the llm participant is still the one an agent session posts as.
- **Data:** `usage.json`, every `index.json`, `runs.json` and `projects/<id>/corpora/`. Export and import carry no corpora, destinations or runs; an export from before still imports, with those parts dropped.
- **Tests:** `Llm`, `Workers`, `Worker`, `WorkerUi`, `WorkerApp`, `Index`, `Vectors`, `Zip` and `Filter`; `Api` and `Ui` lose their LLM, worker and corpus cases.
- **The guide** `.guides/build-with-consensus.md` (and `GET /instructions`) stays, rewritten for what remains: the API, the turn, the build loop of an agent session. Review, Build and workers come out of it.

### The settings modal

- **Settings** in the header (owner only) opens a modal over `consensus.json`: `Host` and `Port` (applied at the next start, said so in the modal), `States` (the list, one per line; a state in use by a plan cannot be removed), `Participants` (Name, Display, Role; a token shown, copied or renewed per participant), and the theme and scale (below).
- The modal reads and writes through two new routes, `GET /api/settings` and `PUT /api/settings` (owner only; the whole object, checked as at start). Everything but Host and Port applies at once.
- The rest of the modal is the same validation the server runs at start, with the problems shown in it; nothing is saved while there are problems.

### Theme and style

- `Theme` (light, dark or system) and `Scale` (small, normal or large) live in the settings as the server's defaults: what every browser starts with. The header's two selectors stay and override them for that browser only, kept in its storage as today; a **Use server defaults** choice clears the override.

### The Context folder

- Every project has a folder named **Context** at its root, first in the tree, holding its **Context** document. The folder is not renamed, moved or deleted, and nor is the document; both are made with the project. The folder holds documents only, no folders and no plans; **New Document** is offered there and nowhere else. The rest of the tree holds folders and plans (Subplans included).
- The kind `context` goes: the Context document is a document like any other, with revisions and no threads. `project.json` keeps `Context` as the id of that document.
- At the server's first start on existing data, each project's context proposal becomes the Context document in a new Context folder, and any document elsewhere in the tree moves into the Context folder, keeping its name. Corpora in the tree go to the trash. The migration runs once and says what it did on the console.
- An agent session reads the Context folder's documents for the project's background (plan Agent Instructions says how), as it reads the context today.

### After Step 1

- `npm test` is the remaining suites; the Docker image is rebuilt and loaded on cube4, which migrates its data at start.
- `readme.md` and `.guides/build-with-consensus.md` describe the server as it then is.


## Step 2: Consensus Desktop Application

The Consensus Web UI will be packaged as an Electron application for use as a local desktop application. The application will serve as Consensus client which can connect to any accessible Consensus web server.

The application will be able to spawn a single local Consensus server given the server's data folder which includes the configuration file for that server. When running a local server, the desktop application will connect to this local server.

In order to connect to multiple Consensus servers (local and remote), multiple instances of the application must be run.

### The app

- Electron, in this repo under `desktop/`: `desktop/main.js`, `desktop/preload.js` and the app's own small page in `desktop/page/` (the connect screen). `electron` is a devDependency of the root package and `npm run desktop` starts it from the checkout, as the worker app did.
- The Consensus page itself is not bundled: the window loads it from the server it is connected to (`http://<host>:<port>/`), so the page always matches the server. A request from the app carries no token and is the owner, as a browser is today.
- The app's settings are `desktop.json` in Electron's user-data folder (`%APPDATA%/consensus-desktop/`): `Servers` (each a Name and a Url), `Local` (the data folder, and the port from its `consensus.json`), and `Last` (what was open).

### Connecting

- The app opens on the **connect screen**: the saved servers, each with Connect, Edit and Remove; Add server (Name, Url, tried before it is saved); and **Local server** with the data folder (Browse), Start and Stop. The screen says what it is connected to.
- **Local server:** started in the app's process through `Start` from `src/Server.js` with the chosen data folder, on `127.0.0.1` and the folder's port; a missing `consensus.json` is written with the defaults at that first start, as the command line does. The app connects to it as soon as it listens. Stop closes it; closing the window stops it too.
- Once connected, the window shows the Consensus page, with **Server** in the app's menu: Connect to another (back to the connect screen), Reload, and the local server's Start and Stop. The connect screen is also where an unreachable server lands you, with the reason.
- A second server at the same time is a second instance: **New window** in the Server menu starts another instance of the app with the same `desktop.json`, on its own connect screen.
- A tab's **Detach** opens a new window of the app, as a browser pop-up does today.

### What stays the same

- The server and its page are not changed for the app, beyond allowing the page to be loaded by it. The desktop is a client: everything it shows comes from the server it is connected to.

### After Step 2

- Tests: `node --test` for the app's settings module and the local server's start and stop with the real `Start` over a temporary folder; the window checked by hand, as for the worker app.


## Step 3: Local LLMs and Workspaces

LLM Connections and Workspaces will be reintroduced into the desktop application. Users can add these connections within the `Context` folder.

### The sketch

- LLM connections (claude-cli, ollama) and workspaces (a local folder, with Include and Exclude) are the desktop's, kept in `desktop.json` per server and project, never in the server's data. The Context folder of a project shows them, in the desktop only, as items of its own kind beside the documents: each opens to its settings.
- The desktop takes the LLM's turn with the local model and the local files: it reads what waits on the llm from the server, runs the model with the workspace's files and the Context folder's documents at hand (the tool loop and the file tools come back from the worker's code), and posts the replies and applies through the server's API as the participant the LLM connection names (the llm participant by default); no tokens are involved, and user management is a later plan of its own. Review returns as a button in the desktop, not in the server's page.
- Builds (implementing a plan in a workspace) and git are decided in Step 3's own plan.
